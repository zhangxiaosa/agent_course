09 / CONTROL

控制流中间件

前五个中间件改的是数据、权限、记录。这一类改的是图本身：它不走"下一步"，而是往回跳。一个 agent 能不能自我纠正，就取决于有没有这条回边。

① 重试：在 after_model 往回跳

模型调用失败是常态——429 限流、超时、上游抖动。失败只能在这一轮调用返回之后才知道，所以挂点只能是 after_model，然后 jump to before_model。

after_model · retry
尝试记录

重试间隔不能是常数。如果所有失败请求都按同一间隔同时重发，上游会在重试时刻再次收到与失败数量相同的请求量，负载峰值只是被平移了一次，并没有消失，整批重试通常仍会失败。所以间隔要同时带指数增长和随机抖动，把重试时刻分散开：

1s
2s
4s
8s
＋ jitter 0–20%

delay = min(base × 2^attempt, cap) × (1 + random × 0.2)。加那点随机量的目的不是"更快"，是把同时到达的请求错开。没有 jitter 的话，一万个客户端还是会在第 4 秒一起撞上来。

重试的前提是幂等。模型调用没有副作用，重试一百次也安全；工具调用不是——create_order 超时后重试，可能下了两单。所以重试策略要按节点分开：模型节点可以激进，工具节点必须先查幂等键，或者干脆不重试、转人工（回到第 08 章）。

② 评审：在 after_agent 把结果打回去

这是最容易被忽略、但作用最大的一条。模型说"做完了"，循环就退出了——但模型判断自己完成的标准，和任务真正完成的标准，往往不是一回事。

还是第 04 章那个案例：目标是"找出所有带高危漏洞的包"，模型只修了 Django 和 requests 就宣布结束。after_agent 上的 judge 拿着最初那句 goal 去核对，发现漏了 pyyaml。

after_agent · evaluator
messages 记录

关键在 feedback 怎么插。它不是一条新的 user 消息——那会看起来像用户改了需求。实际实现里通常是一条 role:"judge" 或 role:"system" 的批评，明确写出缺了什么、依据是什么：

{ "role": "judge",
  "content": "goal 要求覆盖所有高危包。当前结果只处理了 django 与 requests，
              pyyaml 的 CVE-2020-14343 未修复。请继续。" }

模型下一轮就会去读那个包。注意它不会重头再来——messages 里已有的上下文全在，它接着干。

judge 用什么判适合代价
硬规则有明确验收条件的：测试通过、文件存在、格式合法最便宜最可靠，但只能查"能不能"，查不了"好不好"
另一个模型 + rubric开放式任务：报告、代码质量、需求覆盖度多一次调用；judge 也会看走眼
人工高风险交付回到第 08 章，慢但兜得住
评审必须设上限。judge 苛刻一点，模型改一点，judge 还不满意——这个环可以转到天荒地老，token 一路烧。max_evals 是硬约束，到顶就交给人，或者带着"未完全达标"的标记退出。任何往回跳的边都要有次数上限，这是控制流中间件的通用规则。

六个中间件的共同点

回头看它们的共同点：每一个都是 (hook, handler)——挂在某个节点上，看当时的上下文，决定改数据还是改流向。

中间件挂点动作闭环了什么
压缩before_model改 messages（少）上下文不会爆
卸载after_tool改 messages（换页）工具不会撑爆上下文
可观测全部只读，不改出了问题能查、能算账
审批before_tool停住，等人危险动作有人兜
重试after_modeljump 回 before_model瞬时失败不终止任务
评审after_agent插 feedback + jump 回"声称完成"不等于完成

中间件是一切行为的闭环。它可评测（评审）、可介入（审批）、可影响记忆（压缩与卸载）、可观测（trace）、可容错（重试）。一个 agent 的能力上限由模型决定，但它的可靠性和可运维性，几乎完全由这一层决定。
