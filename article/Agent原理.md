# Agent 基本原理和演进

Agent 的技术演进可以归纳为一条因果序列：每个环节解决一个问题，同时留下一项新的问题，交由下一个环节处理。语言模型提供理解与生成能力，但不具备行动能力；工具调用提供行动能力，但一次只能完成一个动作；循环将两者组合为可重复的流程，同时把上下文管理、执行安全与完成判定交给模型自身；中间件在这些位置施加约束，使行动变为可控、可查、可回退的过程。

| 环节 | 内容 | 解决的问题 | 遗留的问题 |
| --- | --- | --- | --- |
| 模型 | 语言模型 | 将模糊意图转换为可计算的概率分布，再采样出下一个 token | 只能生成语言，不能执行动作；观察不到外部环境 |
| 工具 | 工具调用 | 模型输出结构化参数，宿主执行并把结果回填上下文 | 执行由宿主完成，一次只支持一个动作，往复过程缺少机制承载 |
| 循环 | ReAct 循环 | 把模型调用与工具执行串成 while 循环 | 上下文只增不减；参数不经检查即进入执行器；任务是否完成由模型判断 |
| 中间件 | 拦截层 | 在循环各节点插入压缩、卸载、审批、重试、验收 | 收益取决于钩子设计是否准确 |

该序列中每一环都不是并列模块，而是上一环缺陷的产物。

## 一、语言模型的四次跃迁

语言模型解决的问题只有一个：把一句模糊的意图压成一个可计算的分布，再从其中采样出下一个 token。2022 年底的 RLHF 使模型从续写文本转向遵循指令，agent 由此第一次拥有可遵循指令的模型。但模型的输出只有语言一种形式，既没有执行能力，也观察不到外部环境；即使给定文件路径，内容仍只能依靠推测。

### 1. 奖励信号换了四次

**RLHF（2017 → 2022-11-30）。** 2017 年，Christiano 等人解决了「如何把人类偏好变成一个可优化的奖励函数」；2019 年，Ziegler 把这一方法用到语言模型上；2022 年 3 月的 InstructGPT 拼齐了完整三步——人工示范做 SFT 冷启动、对同一问题的多个回答排序训出奖励模型、再用 PPO 以奖励模型为裁判优化生成策略。同年 11 月 30 日上线的 ChatGPT，把同一套流程推到产品级体量。

质变不在知识量上，在行为上：base 模型顺着输入向下续写，RLHF 之后的模型回答输入中提出的问题。这是第一次质变，不是第一次发明。对 agent 的意义可以概括为：模型从补全文本，变成以人类偏好的方式（对话）补全文本。

**Function calling（2023-06-13）。** GPT-4 于 2023 年 3 月发布，此后不久，同一个模型系列上开始出现 function calling。模型第一次把「说什么」与「做什么」分开：文字给人看，参数给程序用。模型必须读懂工具 schema，把自然语言意图映射成合法参数。

代价是一类新的错误：幻觉出不存在的函数名、漏掉必填字段、把字符串写入数字字段。因此每一层工具调用都需要 schema 校验。

**长思维链（2025-01-20）。** 这里常被记混：带来「思考」的不是 DeepSeek-V3，而是 DeepSeek-R1。V3 于 2024 年 12 月发布，671B 总参 / 37B 激活的 MoE，是 R1 的基座，本身不做长思维链；R1 才是把思考训出来的模型。R1-Zero 不做 SFT，直接采用 GRPO 与规则化奖励：答案正确给 +1，错误给 −1，中间过程不作约束。结果是模型自行学会延长思考、回头验算、换一条路径重试，AIME 2024 从 15.6% 提升到 71.0%。

推理第一次变成一段可训练、可计费、可观察的输出，而不是藏在权重中的倾向。代价是思考 token 直接计费：同一道题思考 3000 token 与思考 200 token，成本相差 15 倍，延迟同步翻倍。

**Agentic RL（2025 上半年）。** 此前的 RL 都在训练文本推理；agentic RL 把工具执行放进 rollout：模型生成到一半插入工具调用，取得真实返回后继续生成，奖励只在轨迹终点给一次。

- ReTool（2025-04）：代码解释器进入 RL 循环，AIME24 达到 67.0%（400 步），纯文本基线为 40.0%（1080 步）。RL 之后回答长度反而缩短约 40%，因为算得准便不再需要猜测。
- Kimi K2（2025-07）：agentic 数据合成与联合 RL 做成完整管线，工具从 3000 个真实 MCP 演化到 20000 个合成工具，任务采用 rubric 化判定，仅保留成功轨迹。

代价由环境承担：沙箱、真实仓库、模拟用户，并且要判得出成败，成本比纯文本 RL 高一个数量级。

### 2. 四次跃迁，改的都不是参数量

模型规模在稳定增长，但真正带来能力断层的，是奖励信号换了一种。

| 跃迁 | 训练信号 | 能力增量 | 同时引入的新问题 |
| --- | --- | --- | --- |
| RLHF | 人类对两个回答的排序 | 从「续写」变成「回应」 | reward hacking |
| function call | 指令微调 + schema 约束解码 | 输出可被程序消费 | 参数不符合 schema |
| 长思维链 | 答案是否正确（可规则验证） | 多步推理、自我检查 | 成本高 |
| agentic RL | 整条轨迹的最终任务成败 | 自行判断何时使用哪个工具 | 绑定训练时的环境 |

五项能力标签按时间顺序依次具备：对话、配合人类、调用工具、长链推理、自主多步执行。RLHF 具备前两项；function calling 增加「调用工具」；长思维链增加「长链推理」；agentic RL 最后增加「自主多步执行」。

每一次能力跃迁都会引入一个新的不可控因素，中间件的作用就是在这些位置上做约束。

## 二、工具调用的演进

工具调用解决的问题是行动：模型输出结构化参数，宿主执行，结果作为一条消息回填上下文。模型由此可以读取文件、执行命令、查询数据库，无需依赖推测。

同一个需求在三个阶段差别很大：**统计 `app.py` 中 `start_app` 出现的次数**。

### 1. function calling（2023-06-13）

模型只输出一条 JSON：

```json
{
  "tool_calls": [{
    "id": "call_a1",
    "type": "function",
    "function": {
      "name": "run_shell",
      "arguments": "{\"cmd\":\"grep -n start_app app.py\"}"
    }
  }]
}
```

宿主完成四件事：按路由表找到函数、用 schema 校验参数、执行、把结果作为 `role:"tool"` 消息回填。grep 返回 37 行匹配结果，整段进入上下文；第二轮模型自行逐条数过，输出「一共 37 次」。该数值由模型逐条清点得出，而非由工具计算得出。计数环节由模型承担；工具数量增加时，宿主要维护的路由与校验也随之增加。

`arguments` 是字符串而非对象，模型经常在此处遗漏转义，`JSON.parse` 失败只会在宿主侧抛错。

### 2. MCP（2024-11-25）

模型侧输出基本未变：

```json
{"type":"tool_use","id":"tu_7","name":"run_shell","input":{"cmd":"grep -n start_app app.py"}}
```

改变的是工具清单的来源：宿主启动时向每个 MCP Server 拉取一次 `tools/list`，调用走 `tools/call`，由 JSON-RPC 2.0 承载，传输可以是 stdio 或 HTTP。

```
→ {"jsonrpc":"2.0","id":7,"method":"tools/call",
   "params":{"name":"run_shell","arguments":{"cmd":"grep -n start_app app.py"}}}
← {"jsonrpc":"2.0","id":7,"result":{"content":[{"type":"text","text":"..."}],"isError":false}}
```

grep 的 37 行仍然整段返回并写入上下文，计数仍由模型完成。差异仅在于该命令由哪个 server 提供。宿主不再维护路由表，只维护一份「server 与 tool」的对应索引；新增工具只需挂载新的 server，宿主侧无需修改。

### 3. MCP 统一的内容

常见的误解是 MCP 改变了模型的输出格式。实际上模型侧仍然是 `tool_use` 块，与 function calling 时代一致。MCP 标准化的是另一侧内容：工具定义的发现方式、调用方式与结果返回方式。

没有 MCP 时是 N×M 的适配：三个宿主各自维护适配层对接四家工具，组合数为 12；接入 MCP 之后，宿主只接协议、工具只暴露 server，组合数降为 3+4。

协议用 JSON-RPC 2.0 定义了三个原语：`tools`（可调用的动作）、`resources`（可读的数据）、`prompts`（可复用的模板）。传输层可以是 stdio，也可以是 HTTP。「写一次工具，供所有客户端使用」由此成为可能——这是该协议被称为里程碑的原因：价值不在技术难度，而在把生态的边际成本降了下来。

### 4. code-as-action

前两个阶段都在优化「参数如何传递」，但受同一项限制：一次工具调用只能表达一个动作。上述需求中，grep 是第一步，计数是第二步——第二步没有对应工具，只能由模型在上下文中统计。

CodeAct（2024-02）的主张是把动作空间从「一组函数签名」换成「一段可执行代码」：

```bash
grep -n start_app app.py | wc -l
# → 37
```

过滤与计数在同一段脚本中完成，中间结果留在管道内，没有进入上下文。宿主只需提供一个沙箱，回传给模型的是 stdout 中的「37」，上下文仅增加两个字符。

| 维度 | function calling | MCP | code-as-action |
| --- | --- | --- | --- |
| 模型输出 | 函数名 + JSON 参数 | 同左（协议不碰模型侧） | 一段代码 |
| 一次能表达几步 | 一步 | 一步 | 任意多步，含控制流 |
| 中间结果 | 全部写入上下文 | 全部写入上下文 | 留在沙箱里，只回传最终值 |
| 主要风险 | 函数名幻觉、schema 不合 | 同左 + 服务器信任边界 | 任意代码执行，必须强沙箱 |
| 成熟度 | 事实标准 | 事实标准（2025 年主流客户端全支持） | 方向明确，标准未定 |

上下文成本最低的做法，是根本不产生那些 token。这一点直接引出后续的记忆中间件。

安全边界随协议逐层下沉：function calling 时代危险动作在宿主侧被路由表挡住；MCP 时代工具来自第三方服务器，宿主需要决定信任范围；code-as-action 时代模型直接写 shell，沙箱成为唯一防线。协议自由度越高，人工审批层越有必要保留。

## 三、Agent 的形态谱系

同样的模型与工具，换一种拓扑就能解决完全不同的问题。形态不是风格选择，而是成本与可控性之间的权衡：结构越自由，越能处理未知路径，也越难预测下一步动作。

五种形态按自由度从低到高排列。

| 形态 | 拓扑 | 调用次数 | 可预见性 | 典型场景 |
| --- | --- | --- | --- | --- |
| CoT | 直线 | 1 ~ n 串行 | 高 | 推理、格式转换 |
| ToT | 树，可回溯 | 分支 × 深度 | 中 | 调优、方案比选 |
| Plan-and-Execute | 两段式 | 1 + n | 高（计划冻结） | 长任务、需人审 |
| 工作流 | 图，人工预定义，可带环 | 节点数 | 最高 | 稳定流程、要审计 |
| ReAct | 环 | 不定，受上限约束 | 最低 | Coding、开放任务 |

### 1. Chain of Thought：一条直线

问题 → 步骤 1（拆解）→ 步骤 2（代入）→ 结论。

每一步的输出直接成为下一步的输入，不存在分支；需要修改时只能重新开始。适用于路径唯一、不需要外部信息、步骤可预见的任务。步骤数量较多时，前后内容容易自相矛盾，且缺少发现错误的机制。

### 2. Tree of Thought：可回溯的树

搜索式问题无法沿单一串行路径完成，需要展开为树结构。以参数调优为例：

- 分支 A：将参数 a 上调 1，再次上调 1，第三次上调 1，逐层评估指标变化；
- 分支 B：将参数 b 下调 10%，再次下调 10%，沿该路径继续展开；
- 两条分支各自衍生新的组合，三层之后候选数量迅速增长——这就是组合爆炸。

```
                 初始配置
                /        \
         a +1            b −10%
        /    \           /     \
   a +1      a −1     b −10%   b +10%
   /  \       /  \      /  \      /  \
 ...  ...   ...  ...  ...  ...  ...  ...
        （剪枝：分数低于阈值的分支不再展开）
```

工作方式是：生成 N 个候选 → 评估器打分 → 保留 top-k → 对每个保留项继续展开 → 所有分支均被剪除时回溯至上一层，更换分解方式。调用次数等于分支数乘以深度，因此评估器必须可靠，否则剪枝等同于误剪——误剪有效分支的代价高于不剪枝。

### 3. Plan-and-Execute：先冻结，再执行

Planner 一次调用产出完整计划，Executor 逐条执行且不重新读取计划，全部执行完成后由 Replanner 决定收尾还是补充一步。

优点是计划可供人审阅、可中途暂停、可替换执行器；缺点是计划在第一步之前就已固定。真实环境常在第 3 步给出计划中未写明的信息，此时要么按原计划执行完毕（结果错误），要么重新生成完整计划（成本浪费）。

### 4. 工作流：人工预定义的图

节点由人预先定义，可以包含路由、并行与汇总，也可以包含环。

```
start → router·分类 ─┬→ 日志检索 ─┐
                     ├→ 变更记录 ─┼→ merge → diagnose·出结论 → end
                     └→ 相似工单 ─┘
```

router 按输入类型分流：一类走「读日志」，一类走「查变更」。中间三个节点并行执行，由 merge 汇总为证据集合，交给 diagnose 出结论。这种结构可预见性最高、最易审计，代价是只能处理预先枚举的分支。

### 5. ReAct：一个循环结构

```
start → model_call ─┬→ tool_call →（回到 model_call）
                    └→ end
```

model_call 之后只有两种去向：需要外部信息则进入 tool_call，不需要则直接到 end；tool_call 始终返回 model_call。这是五种形态中自由度最高、也最难预测的一种，因此必须配置上限。

## 四、ReAct 循环

循环解决的问题是把模型调用与工具执行接成可重复的流程：

```
messages = [system, user]
while True:
    resp = model(messages)              # 全量重放
    if resp.tool_calls:
        for call in resp.tool_calls:
            out = run(call)             # 宿主的执行器
            messages.append(tool_result(call.id, out))
    elif resp.finish_reason == "stop":
        break
```

### 1. 每一次都要完全重放

模型不具备跨轮次状态，不保留上一轮读取的内容。所谓记忆，指把此前全部消息重新送入上下文，使模型基于全文预测下一步。因此循环每次迭代，输入都比上一次更长。

一次实际运行：5 轮模型调用、4 轮工具往返，累计输入 8,944 token。每次调用都把此前产生的全部 token 重新送入模型，用于预测下一步；真正新增的内容不足 400 token，其余均为重放。

1,180 → 1,486 → 1,690 → 2,140 → 2,448，该序列即构成成本增长曲线。

### 2. 三种退出条件

| 出口 | 判定方式 | 缺失后果 |
| --- | --- | --- |
| 模型判断完成 | `finish_reason = "stop"`，且本次响应不含 `tool_calls` | —— |
| 回合上限 | `turn >= max_turns`（常见 20–50） | 模型反复调用同一工具，无法收敛 |
| 预算上限 | 累计 token 或墙钟时间超阈值 | 单次失控任务耗尽整月额度 |

`finish_reason="stop"` 只说明模型本次没有继续输出，不代表任务已经完成。两者的差距，正是评审中间件存在的原因。

### 3. 三个局限

循环运转之后，问题由「是否可行」转向成本、稳定性与正确性。三个局限对应后续三组中间件：

1. **上下文只增不减。** 历史全集重放，第 30 轮时 prompt 中积累大量已无用的目录列表。处理方式：上下文压缩与工具输出卸载。
2. **参数不经检查即进入执行器。** 模型生成 `rm -rf`，框架按原样执行。处理方式：`before_tool` 挂起，等待人工审批。
3. **任务是否完成由模型自行判断。** 模型认为完成时，任务未必真的完成。处理方式：`after_agent` 增加一次验收判定，不通过则退回并继续执行。

三个问题都无法通过修改提示词解决，只能在循环节点上插入可复用的拦截层。

### 4. messages 结构的两处硬约束

- **`tool_call_id` 必须配对。** 每一条 `tool` 消息都要指回某个 `assistant.tool_calls` 中的 id。配对断裂时请求直接返回 400，不是效果变差，而是请求无法发出。
- **工具结果必须紧跟发起该调用的 assistant 消息。** 顺序错误会让模型先看到结果、后看到动作，模型行为会出现偏差。

## 五、中间件

循环可以运转之后，缺少的是在正确位置介入的能力。这组能力的共同形式是钩子：在某个节点之前或之后插入一个处理函数，读取 state、改写 state，或者决定不进入下一个节点。

### 1. 钩子的位置

前述 4 节点简化结构，展开后为 8 个节点：

```
  before_agent ──────┐
                     ↓
  before_model → model_call → after_model ──┬→ before_tool → tool_call → after_tool ─┐
                     ↑                      └→ after_agent                                │
                     └──────────────────────────────────────────────────────────────────┘
```

沿该路径完整执行一次即为一轮：`before_agent` 在开始前执行一次，`before_model` → `model_call` → `after_model`；需要执行动作时进入 `before_tool` → `tool_call` → `after_tool`，随后回到 `before_model` 开始下一轮；不需要执行动作时由 `after_model` 直接交给 `after_agent` 收尾。可插入处理逻辑的位置只有这 8 个。

钩子不是新增节点，而是两个节点之间的执行间隙：在该位置可以读取状态、修改状态，也可以决定跳过下一个节点。

### 2. 中间件 =（hook, handler）

处理函数接收 state，返回 state 或一条跳转指令。后续五个中间件均属于下表所列的用法。

| 中间件 | 挂载位置 | 解决的问题 | 代价 |
| --- | --- | --- | --- |
| 上下文压缩 | before_model | 历史只增不减，第 30 轮 prompt 中均为已无用的目录列表 | 摘要有损，细节丢失后无法找回 |
| 工具卸载 | after_tool | 一次 `ls -R` 将数万行内容写入上下文 | 模型需要多一次调用读回全文 |
| 人工审批 | before_tool | 模型直接生成 `rm -rf`，框架按原样执行 | 每次打断都有人工成本，高频场景难以坚持 |
| model retry | after_model | 429、超时、5xx 直接终止整个运行 | 重试会叠加上游负载，需要退避与抖动 |
| evaluator | after_agent | 模型声称完成，实际只完成一半 | 多一次判定调用；判定错误会导致反复回退 |

这五个中间件并非五种独立功能，而是同一种结构的五种用法。设计上的关键问题不是是否需要某项能力，而是该能力应挂载在哪个位置。

## 六、记忆：压缩与卸载

循环存在两个无法回避的约束：历史只增不减，工具输出没有上限。两者叠加，到第三十轮时 prompt 中已积累数万 token 的无效目录列表。对应的两种处理方式是压缩历史与卸载工具输出。

### 1. 压缩：一次实际的重写

第 12 轮，上下文 41,200 token，窗口预算 32,000。模型尚未被调用，该轮请求已无法发送。

压缩中间件在 `before_model` 介入：挑选 turn 3–9 的 14 条消息交给小模型做摘要。区间选择有明确约束——system、首条用户需求、最近 3 轮必须原样保留，只能压缩中间区间中「已使用完毕、但仍占用位置」的历史。

摘要返回后：14 条变为 1 条，用 4,200 token 替换原来的 28,000，上下文从 41,200 降到 12,930。`messages` 数组被就地改写，该 14 条消息被移除，而 system 与开头那条用户需求仍留在原位。

模型接收的是该压缩版本，不会察觉历史曾被压缩。省下的 28,270 token 是这一轮的实际成本节省。

### 2. 压缩必须保留的内容

摘要并非单纯缩短历史，其目标是在有限预算下保留模型作出判断所需的最小信息集。

| 必须保留 | 压缩后的后果 |
| --- | --- |
| system prompt 与首条需求 | 前者包含工具定义，后者是本次任务的目标。剔除工具定义后，模型不再知道自己有哪些工具；丢失首条需求后，后续所有判断都失去依据 |
| 最近 N 轮 | 当前这一步的判断依据均位于此处。压缩后模型会丢失刚刚读取到的内容 |
| tool_call_id 配对 | 每一条 tool 消息都要对应一条 assistant.tool_calls。配对破坏后，请求直接返回 400 |
| 失败过的路径 | 「这条路径尝试过，报错 xxx」是模型避免重复尝试的唯一依据。缺失该条后，模型会在第 14 轮再次执行同一条命令 |

摘要本身还需要一次模型调用。压缩频率过高（例如每轮都压缩），付出的是「压缩调用 + 原始历史」两份成本。实践中通常只在超过阈值时压缩一次，压到 40% 左右，为后续增长留出空间。

### 3. 卸载：按位置裁剪，按字节存储

工具输出属于另一类问题：单条即可超过阈值。`read_file` 返回 18,400 字符，其中约 17,000 字符是依赖下载的进度行。

处理方式是保留开头 400 字符（供上下文使用）、末尾 2,000 字符（结论位于此处），中间 16,000 字符写入磁盘文件 `result_c7.txt`，并插入一条提示「如需完整内容请加载」。上下文从 19,380 降到 3,382。

保留末尾而非开头的原因：`build.log`、`pytest`、`npm install` 这类输出，结论位于最后——前部数万行为依赖树与进度条，末尾十行才包含 `ERROR / FAILED / exit code`。裁掉开头、保留末尾，模型通常不需要读回全文即可判断；裁掉末尾、保留开头，等于丢弃最有用的部分并保留最无用的部分，模型会立即再次调用工具读回，多花一次往返。

裁剪并非丢弃，其性质等同于换页：全文必须仍然存在于某个位置，否则模型一旦真正需要中间那段，就永久失去。

### 4. 两种处理方式的机制对应关系

操作系统早已使用类似的分工：

| 操作系统 | 对应到 agent | 触发条件 | 回退手段 |
| --- | --- | --- | --- |
| 精度截断 | 上下文压缩 | token 超预算 | 摘要只保留粗粒度事实（原始细节不可还原） |
| 换页到磁盘 | 工具输出卸载 | 单条消息超阈值 | 按 `result_<id>.txt` 读回（无损） |
| 按需调入 | 长期记忆检索 | 新会话开始 / 相关度命中 | 向量召回 top-k 注入 |

两者的区别在于可逆性：卸载可以无损读回，压缩不能。缓存逐出不属于这一类——被淘汰的页仍可重新读回，信息并未真正消失。

### 5. 完整的记忆系统

压缩与卸载只解决容量不足。真实产品中还存在第三个问题：应记录的内容未被记录。用户上周说明「只用 Python 3.11」，本周开启新会话时，agent 对此一无所知。

| 层 | 存储位置 | 存储内容 | 取回方式 | 写入方 |
| --- | --- | --- | --- | --- |
| 短期记忆 | checkpointer 中的 messages；state / scratchpad | 最近 N 轮与当前任务；计划、待办、已确认的事实 | messages 直接进入 prompt；state 每轮注入 system 末尾 | 循环自动追加；中间件读写 |
| 长期记忆 | 向量库 + 图 | 跨会话偏好、项目知识、失败教训 | 检索 top-k 注入 | 写入前需抽取、去重、合并 |
| 归档 | 对象存储 / 文件 | 原始工具输出、大文件、历史版本 | 按 id 按需加载 | 卸载中间件 |

长期记忆的难点不在检索，而在写入。写入过少不起作用，写入过多则造成污染：同一个偏好记录五条、三条互相矛盾、一条早已过期。因此成熟的记忆系统都有一套后台流程：抽取候选、去重合并、按时间衰减、定期清理。

实践顺序是：先做卸载，再做压缩，最后做长期记忆。前两者是确定性的、可测量的（节省了多少 token 可以直接观察）；长期记忆是概率性的，过早引入只会产生大量检索噪音。

## 七、人工审批

前述中间件均修改数据，只有审批修改控制流：可以让循环停下来，等待人工判断。挂载点在 `before_tool`——这是最后一个「命令尚未执行」的位置。

### 1. 为什么必须挂在这里

| 挂载点 | 可见信息 | 能否阻止 |
| --- | --- | --- |
| before_model | 历史、目标 | 能阻止调用模型，但无法拦截具体命令——参数尚未生成 |
| after_model | 即将调用的工具名与参数 | 能，但在此处拦截等于丢弃模型的输出，语义不清（模型会认为自己已经发出） |
| before_tool | 工具名 + 完整参数 | 能，且是唯一语义清晰的位置——拒绝即表示该命令未执行 |
| after_tool | 执行结果 | 不能。只能事后补偿（回滚、告警） |

`before_tool` 上的一次挂起按如下路径处理：

```
模型生成 tool_call
  → before_tool（处理函数判定：需要人工）
  → 挂起，把「工具名 + 完整参数」推入审批队列
  → 人工批准：继续执行 tool_call
  → 人工拒绝：写回一条 tool 结果「用户不同意」，模型走降级路径
```

拒绝不能只返回一句「不同意」。模型很可能直接重试同一条命令，原因是无法判断被拒绝的缘由。需要附带理由：「用户不同意执行 `rm -rf /var/cache/*`，理由是范围过大」——模型下一轮会改为 `find -mtime +7`，这种反馈才具有可操作性。

### 2. 应当拦截的范围

| 信号 | 观察内容 | 典型规则 |
| --- | --- | --- |
| 命令动词 | 破坏性动作 | rm、dd、mkfs、DROP TABLE、truncate |
| 作用范围 | 是否存在通配符、递归或绝对路径 | `*`、`-r`、`/**`、系统目录（/etc、/var、~/.ssh） |
| 外发方向 | 数据是否离开本机 | `curl -d @file`、scp、发送邮件、写外部 API |
| 权限升级 | 是否要求更高权限 | sudo、chmod 777、修改 SSH 配置 |
| 不可逆性 | 是否存在回退路径 | 删库、强推、覆盖未提交的工作区 |

规则要准确，数量要少。审批机制最大的风险是疲劳：一个 agent 每次运行都弹出三次确认，使用者在第三天便会无意识点击同意，此时审批层不仅没有保护作用，还会带来虚假的安全感。

### 3. 三种降级方式

**dry-run（先预演，不执行）。** 将命令替换为仅输出、不写入磁盘的形式先执行一遍。`rsync -av` 加 `--dry-run` 只列出将同步的文件；`git clean -f` 换成 `git clean -n` 只列出将删除的文件；`rm` 没有预演模式，改用 `find` 列出匹配路径。使用者确认影响范围后再决定，多数情况下看完这一步就无需批准。

**改写后放行（批准的是改写版本，不是原文）。** 不改变意图，仅将动作替换为副作用可控的等价形式：

- 换成可恢复版本：`rm -rf /var/cache/*` → 移动到 `trash/cache/`，或 `find ... -mtime +7`；
- 收窄范围：`rm -rf /repo/*` → `rm -rf /repo/build/`；
- 增加保护：`git push --force` → `git push --force-with-lease`。

模型得到的结果是「已执行」，但其影响范围被压缩到一条命令即可恢复的程度，因此不占用一次人工确认。

**规则化分流。** 只读操作自动放行，可逆写操作采用 dry-run 或改写后放行，不可逆、跨边界、涉及外部系统的操作才强制人工。

### 4. 审批记录

审批需要记录：谁批准、何时批准、批准的是哪条命令、当时可见的参数是什么。事后追责依靠的不是日志搜索，而是结构化的审批记录。

超时按 fail-closed 处理。使用者离开现场、审批卡挂起 10 分钟无人处理时，默认放行等同于取消防护。正确做法是超时即拒绝，使模型进入「用户不同意」路径，任务降级但不造成事故。

## 八、控制流

前述中间件改的是数据、权限与记录，这一类修改的是图本身：不进入下一个节点，而是返回之前的节点。一个 agent 能否自我纠正，取决于是否存在该回边。

### 1. 重试：失败后的重试节奏

一次 `model_call` 返回 429。这一类属于可重试：4xx 中的限流、5xx、网络超时均可重试；参数错误与内容审核拒绝不可重试。

重试不应立即重发。全部失败请求在同一毫秒重试，会形成集中的流量峰值——上游刚恢复即再次过载，最终导致重试始终无法成功。因此退避必须是指数加抖动：

```
attempt 1  失败 → 退避 1.2s（±随机抖动）→ jump 回 before_model
attempt 2  仍然 429 → 说明上游确在限流，而非瞬时抖动 → 退避 2.4s
attempt 3  成功 → 继续
```

重试需要上限，并且到达上限时要能交回控制权。重试本身也是一条回边，回边的次数必须被约束。

### 2. 评审：在 after_agent 将结果退回

目标是「找出所有带高危漏洞的包」，模型仅修复 Django 与 requests 即宣布任务结束。`after_agent` 上的 judge 以最初的目标为基准核对，发现遗漏 pyyaml。

完整回路为：模型宣称完成 → judge 判定 2/3 不通过 → feedback 写回 messages → jump 回 `before_model` → 调用 `search_cve("pyyaml 5.4.1")` 取得 CVE-2020-14343 → `model_call` 将工具结果并入结论 → judge 二次评审 3/3 通过 → `agent_end`。

工具返回之后必须有一次模型调用：judge 核对的是模型输出的结论，而不是工具返回值。缺少这一步，judge 将没有可核对的对象。

feedback 的插入方式需要注意：不新增一条 user 消息，否则会表现为用户修改了需求。实际实现中通常使用一条 `role:"judge"` 或 `role:"system"` 的反馈消息，明确指出缺失内容与判断依据：

```json
{ "role": "judge",
  "content": "目标要求覆盖所有高危包。当前只处理了 2 个，
              pyyaml 的 CVE-2020-14343 未修复。请继续，不要重复已完成的。" }
```

judge 的判定方式取决于任务性质：

| 判定方式 | 适用场景 | 代价 |
| --- | --- | --- |
| 硬规则 | 有明确验收条件的任务：测试通过、文件存在、格式合法 | 成本最低、最可靠，但只能检查「是否满足」，无法检查「质量如何」 |
| 模型 + rubric | 开放式任务：报告、代码质量、需求覆盖度 | 多一次调用；judge 也会判断失误 |
| 人工 | 高风险交付 | 速度慢，但可以覆盖 |

评审必须设上限。judge 判定严格、模型仅作小幅修改、judge 仍不满意，这个循环可以无限持续。`max_evals` 是硬约束，达到上限时交给人，或以「未完全达标」标记退出。

### 3. 五个中间件的汇总

| 中间件 | 挂载点 | 动作 | 闭环的问题 |
| --- | --- | --- | --- |
| 压缩 | before_model | 改写 messages（减少） | 上下文不会溢出 |
| 卸载 | after_tool | 改写 messages（换页） | 工具输出不会超出上下文预算 |
| 审批 | before_tool | 挂起，等待人工 | 危险动作有人确认 |
| 重试 | after_model | jump 回 before_model | 瞬时失败不终止任务 |
| 评审 | after_agent | 插入 feedback + jump 回 | 「声称完成」不等于完成 |

中间件构成 agent 行为的闭环：可评测、可介入、可影响记忆、可容错。agent 的能力上限由模型决定，而可靠性与可运维性几乎完全由这一层决定。

## 结语

归纳这条链：语言模型提供理解与生成能力，工具提供对外触达，循环将两者组合为行动，中间件使行动可控、可查、可回退。

模型调用、工具执行、把两者串起来的循环，以及位于循环外部的拦截层。更换任一框架时，名称会变化，位置保持一致。
