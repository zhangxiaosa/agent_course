# Agent 基本原理

我把 agent 的发展和知识压成了一条因果链：每一层解决一件事，同时留下一个问题，下一层来解决它。

链分五层，一层只解决一件事，解决完再把下一个问题交给下一层。

| 层 | 内容 | 解决什么 | 留下什么问题 |
| --- | --- | --- | --- |
| L1 | 语言模型 | 把一句模糊的意图压成一个可计算的分布，再采样出下一个 token | 只能说，不能做；看不见外部世界 |
| L2 | 工具调用 | 模型输出结构化参数，宿主执行，结果回到上下文 | 手是宿主替它动的，一次只动一下，没有机制承载往复 |
| L3 | 循环 | 把 model_call 与 tool_call 串成 while 循环 | 上下文只增不减、参数不经检查就进执行器、任务算不算完成由模型自己判断 |
| L4 | 中间件 | 在循环各节点挂拦截层：压缩、卸载、追踪、审批、重试、验收 | 过程仍然不可见 |
| L5 | 流式前端 | 把内部事件实时推给界面，把过程摊开 | 属于产品层，不再是 agent 本身 |

这不是五个并列的模块，是一条因果链：每一层的能力，都是上一层的缺陷逼出来的。

## 01 · LLM 的四次跃迁

L1 是模型本身。它解决的问题只有一个：把一句模糊的意图压成一个可计算的分布，再从里面采样出下一个 token。2022 年底的 RLHF 把它从「会说话」推成「愿意配合」，agent 第一次有了能听指挥的大脑。

但它只有语言这一个动作。它没有执行能力，也看不见外部世界；你告诉它文件在哪，它也只能猜内容。

### 奖励信号换了四次

**RLHF（2017 → 2022-11-30）。** 2017 年，Christiano 等人先解决了「怎么把人类偏好变成一个可优化的奖励函数」；2019 年，Ziegler 把它用到语言模型上；2022 年 3 月的 InstructGPT 拼齐了完整三步——人工示范做 SFT 冷启动、对同一问题的多个回答排序训出奖励模型、再用 PPO 拿这个奖励模型当裁判去优化生成策略。同年 11 月 30 日上线的 ChatGPT，把同一套流程推到了产品级体量。

质变不在知识量上，在行为上：base 模型会顺着你的话往下续写，RLHF 之后的模型会回答你的问题。这是第一次质变，不是第一次发明。对 agent 的意义可以概括成一句：模型从补全文本，变成以人类的偏好（对话）补全文本。

**Function calling（2023-06-13）。** GPT-4 于 2023 年 3 月发布，此后不久，同一个模型系列上开始有了 function calling。模型第一次把「说什么」和「做什么」分开：文字给人看，参数给程序用。它必须读懂工具的 schema，把自然语言意图映射成合法参数。

代价是新的一类错误：会幻觉出不存在的函数名，会漏必填字段，会把字符串塞进数字字段。所以每一层工具调用都要 schema 校验。

**长思维链（2025-01-20）。** 这里常被记混：带来「思考」的不是 DeepSeek-V3，而是 DeepSeek-R1。V3 于 2024 年 12 月发布，671B 总参 / 37B 激活的 MoE，是 R1 的基座，本身不做长思维链；R1 才是把思考训出来的那个模型。R1-Zero 不做 SFT，直接上 GRPO + 规则化奖励：答案对给 +1，错给 −1，中间过程一概不管。结果模型自己学会了延长思考、回头验算、换一条路重试，AIME 2024 从 15.6% 涨到 71.0%。

推理第一次变成一段可训练、可计费、可观察的输出，而不是藏在权重里的某种倾向。代价是思考 token 直接计费，同一道题思考 3000 token 与思考 200 token，成本差 15 倍，延迟也翻倍。

**Agentic RL（2025 上半年）。** 此前的 RL 都在训文本推理；agentic RL 把工具执行塞进 rollout：模型生成到一半插入工具调用，拿到真实返回再继续生成，奖励只在轨迹终点给一次。

- ReTool（2025-04）：代码解释器进 RL 循环，AIME24 67.0%（400 步），纯文本基线 40.0%（用时 1080 步）。RL 之后回答长度反而缩短约 40%，因为算得准了就不需要瞎猜。
- Kimi K2（2025-07）：agentic 数据合成 + 联合 RL 做成完整管线，工具从 3000 个真实 MCP 演化到 20000 个合成工具，任务是 rubric 化的，只留成功轨迹。

代价要从环境里出：沙箱、真实仓库、模拟用户，还要判得出成败，比纯文本 RL 贵一个数量级。

### 四次跃迁，改的都不是参数量

模型规模在稳定增长，但真正带来能力断层的是奖励信号换了一种。

| 跃迁 | 训练信号 | 能力增量 | 同时引入的新问题 |
| --- | --- | --- | --- |
| RLHF | 人类对两个回答的排序 | 从「续写」变成「回应」 | reward hacking |
| function call | 指令微调 + schema 约束解码 | 输出可被程序消费 | 参数不符合 schema |
| 长思维链 | 答案对不对（可规则验证） | 多步推理、自我检查 | 成本高 |
| agentic RL | 整条轨迹的最终任务成败 | 自己判断何时用哪个工具 | 绑定训练时的环境 |

把五条能力标签摊在一条时间轴上，能看出每一步多点亮了什么：对话、配合人类、调用工具、长链推理、自主多步执行。RLHF 点亮前两个；function calling 补上「调用工具」；长思维链加上「长链推理」；agentic RL 最后补上「自主多步执行」。

这也解释了后面为什么需要中间件：每一次能力跃迁，都会引入一个新的不可控因素，中间件就在这些位置上做约束。

## 02 · 工具调用的演进

L2 是模型长出的手。模型学会输出结构化参数，由宿主执行，结果作为一条消息塞回去。它从此能读文件、跑命令、查数据库，不必再靠猜。

同一个需求，三个阶段差别很大：**数出 `app.py` 里 `start_app` 出现了多少次**。

### 第一阶段：function calling（2023-06-13）

模型只输出一条 JSON，别的什么都没有：

```json
{
  "tool_calls": [{
    "id": "call_a1",
    "type": "function",
    "function": {
      "name": "run_shell",
      "arguments": "{\"cmd\":\"grep -n start_app app.py\"}"
    }
  }]
}
```

宿主做四件事：按路由表找到函数、用 schema 校验参数、执行、把结果作为 `role:"tool"` 消息回填。grep 返回 37 行匹配结果，整段进入上下文；第二轮模型自己数了一遍，输出「一共 37 次」。这个 37 是数出来的，不是算出来的。计数这一步由模型承担，工具越多，宿主要维护的路由与校验就越多。

注意 `arguments` 是一个字符串，不是对象。模型经常在这里漏转义，而 `JSON.parse` 失败只会在宿主侧抛错。

### 第二阶段：MCP（2024-11-25）

模型这一侧几乎没变：

```json
{"type":"tool_use","id":"tu_7","name":"run_shell","input":{"cmd":"grep -n start_app app.py"}}
```

变的只是它怎么知道有这个工具：宿主启动时向每个 MCP Server 拉一次 `tools/list`，调用走 `tools/call`，JSON-RPC 2.0 承载，传输可以是 stdio 或 HTTP。

```
→ {"jsonrpc":"2.0","id":7,"method":"tools/call",
   "params":{"name":"run_shell","arguments":{"cmd":"grep -n start_app app.py"}}}
← {"jsonrpc":"2.0","id":7,"result":{"content":[{"type":"text","text":"..."}],"isError":false}}
```

grep 的 37 行仍然整段回灌，数这 37 行仍然由模型完成。差别只在：这条命令是从哪个 server 拿到的。宿主不再维护路由表，只维护一张「哪个 server 有哪个 tool」的索引；新增工具等于挂一个新 server，宿主零改动。

### MCP 到底统一了什么

这是最容易被误解的一点：MCP 没有改变模型的输出格式，模型那边仍然是 `tool_use` 块，跟 function calling 时代长得一样。它标准化的是另一条边：工具定义怎么被发现、怎么被调用、结果怎么回来。

没有 MCP 时是 N×M 的适配：三个宿主各自维护适配层，对接四家工具，组合数 12。有了 MCP 之后，宿主只接协议，工具只暴露 server，组合数变成 3+4。

它用 JSON-RPC 2.0 定义了三个原语：`tools`（可调用的动作）、`resources`（可读的数据）、`prompts`（可复用的模板）。传输层可以是 stdio，也可以是 HTTP。「写一次工具，给所有客户端用」第一次成为可能——这才是它被称为里程碑的原因：不是技术难度，是把生态的边际成本打下来了。

### 第三阶段：code-as-action

前两个阶段都在优化「参数怎么传」，但它们共享同一个天花板：一次工具调用只能表达一次动作。上面那个需求里，grep 是第一步，计数是第二步——第二步没有对应的工具，只能交给模型在上下文里自己数。

code-as-action 把这个天花板拆了。CodeAct（2024-02）的核心主张是把动作空间从「一组函数签名」换成「一段可执行代码」：

```bash
grep -n start_app app.py | wc -l
# → 37
```

过滤与计数在同一段脚本里完成，中间结果留在管道里，没有进入上下文。宿主只提供一个沙箱，回传给模型的是 stdout 里的「37」，上下文只增加两个字符。

| 维度 | function calling | MCP | code-as-action |
| --- | --- | --- | --- |
| 模型输出 | 函数名 + JSON 参数 | 同左（协议不碰模型侧） | 一段代码 |
| 一次能表达几步 | 一步 | 一步 | 任意多步，含控制流 |
| 中间结果 | 全部回灌进上下文 | 全部回灌进上下文 | 留在沙箱里，只回传最终值 |
| 主要风险 | 函数名幻觉、schema 不合 | 同左 + 服务器信任边界 | 任意代码执行，必须强沙箱 |
| 成熟度 | 事实标准 | 事实标准（2025 年主流客户端全支持） | 方向明确，标准未定 |

上下文成本最低的做法，是根本不产生那些 token。这也直接引出了后面的记忆中间件。

安全边界随协议逐层下沉：function calling 时代危险动作在宿主侧被路由表挡住；MCP 时代工具来自第三方服务器，宿主必须决定信任谁；code-as-action 时代模型直接写 shell，沙箱是唯一防线。协议越自由，人工审批层就越不可省。

## 03 · Agent 的形态谱系

同样的模型、同样的工具，换个拓扑就能解决完全不同的问题。形态不是风格选择，是成本与可控性的权衡：越自由的结构越能处理未知路径，也越难预测它下一步会干什么。

五种形态，按自由度从低到高排。

| 形态 | 拓扑 | 调用次数 | 可预见性 | 典型场景 |
| --- | --- | --- | --- | --- |
| CoT | 直线 | 1 ~ n 串行 | 高 | 推理、格式转换 |
| ToT | 树，可回溯 | 分支 × 深度 | 中 | 调优、方案比选 |
| Plan-and-Execute | 两段式 | 1 + n | 高（计划冻结） | 长任务、需人审 |
| 工作流 | 图，人画，可带环 | 节点数 | 最高 | 稳定流程、要审计 |
| ReAct | 环 | 不定，受上限约束 | 最低 | Coding、开放任务 |

### Chain of Thought：一条直线

问题 → 步骤 1（拆解）→ 步骤 2（代入）→ 结论。

每一步的输出直接成为下一步的输入，没有岔路。想改只能从头再来。适合路径唯一、不需要外部信息、步骤可预见的任务。步骤一长，前后容易自相矛盾，而且没有任何机制能发现它错了。

### Tree of Thought：一棵会回溯的树

搜索式问题不能一条线走到底，要展开成树。以参数调优为例：

- 分支 A：把参数 a 上调 1，再上调 1，再上调 1，逐层评估指标变化；
- 分支 B：把参数 b 下调 10%，再下调 10%，继续沿这条路径展开；
- 两条分支各自还会衍生新的组合，三层之后候选数量迅速增长——这就是组合爆炸。

```
                 初始配置
                /        \
         a +1            b −10%
        /    \           /     \
   a +1      a −1     b −10%   b +10%
   /  \       /  \      /  \      /  \
 ...  ...   ...  ...  ...  ...  ...  ...
        （剪枝：分数低于阈值的分支不再展开）
```

工作方式是：生成 N 个候选 → 评估器打分 → 保留 top-k → 对每个保留项继续展开 → 全部分支剪光时回溯到上一层，换一种分解方式。调用次数等于分支数乘以深度，所以必须有一个靠得住的评估器，否则剪枝就是瞎剪——把好分支剪掉，比不剪更贵。

### Plan-and-Execute：先冻结，再执行

Planner 一次调用出完整计划，Executor 逐条执行、不回看计划，全部跑完后 Replanner 决定收尾还是补一步。

好处是计划可以给人看、可以中途停、可以换执行器；坏处是它在第一步之前就定死了。真实世界会在第 3 步给你一个计划里没写过的东西，此时要么硬着头皮跑完，要么整份重规划。

### 工作流：人画的图

节点是人预先画好的，可以带路由、并行和汇总，也可以带环。

```
start → router·分类 ─┬→ 日志检索 ─┐
                     ├→ 变更记录 ─┼→ merge → diagnose·出结论 → end
                     └→ 相似工单 ─┘
```

router 按输入类型分到两条路：一条走「读日志」，一条走「查变更」。中间三个节点并行执行，再由 merge 汇总成一份证据集，交给 diagnose 出结论。这种结构可预见性最高、最容易审计，代价是它只能处理你预先想到的分支。

### ReAct：一个环

```
start → model_call ─┬→ tool_call →（回到 model_call）
                    └→ end
```

model_call 之后只有两种去向：需要外部信息就去 tool_call，不需要就直接到 end；tool_call 永远回到 model_call。这是五种形态里自由度最高的一种，也是最难预测的一种——所以它必须配上限。

## 04 · ReAct 循环

L3 把 model_call 与 tool_call 串成一个 while 循环：

```
messages = [system, user]
while True:
    resp = model(messages)              # 全量重放
    if resp.tool_calls:
        for call in resp.tool_calls:
            out = run(call)             # 宿主的执行器
            messages.append(tool_result(call.id, out))
    elif resp.finish_reason == "stop":
        break
```

### 为什么每一次都要完全重放

模型没有状态。它不记得上一轮看过什么，所谓「记忆」是把此前所有消息重新送进上下文，让它基于全文预测下一步。所以循环里每转一圈，输入都会比上一圈更长。

一次真实任务：5 轮模型调用、4 轮工具往返，累计输入 8,944 token。每一次调用都把此前产生的全部 token 重新送进模型，让它预测下一步；真正新增的内容不到 400 token，其余都是重放。

1,180 → 1,486 → 1,690 → 2,140 → 2,448，这条曲线就是成本结构的全部。

### 三种退出条件

| 出口 | 判定方式 | 没有它会怎样 |
| --- | --- | --- |
| 模型自觉完成 | `finish_reason = "stop"`，且这次响应里没有 `tool_calls` | —— |
| 回合上限 | `turn >= max_turns`（常见 20–50） | 模型反复调用同一个工具，永不收敛 |
| 预算上限 | 累计 token 或墙钟时间超阈值 | 一次跑飞的任务吃掉整月额度 |

`finish_reason="stop"` 只说明模型这次没有继续输出，不代表任务真的做完了。这两件事之间的差距，就是后面评审中间件存在的原因。

### 三个局限

循环一旦转起来，问题就从「能不能跑」变成「跑得贵不贵、稳不稳、对不对」。三个局限，对应后面三组中间件：

1. **上下文只增不减。** 历史全集重放，第 30 轮时 prompt 里积压着大量早已无用的目录列表。解决方法：上下文压缩、工具输出卸载。
2. **参数不经检查就进了执行器。** 模型生成 `rm -rf`，框架照单执行。解决方法：`before_tool` 挂起，等人审批。
3. **任务算不算完成由模型自己判断。** 它认为它做完了，不代表任务真的做完了。解决方法：`after_agent` 加一道验收，不过就跳回去继续。

三个问题都不是改提示词能解决的，只能在循环的节点上插入可复用的拦截层。

### messages 结构上的两处硬约束

- **`tool_call_id` 必须配对。** 每一条 `tool` 消息都要指回某个 `assistant.tool_calls` 里的 id。配对断了，请求直接返回 400——不是效果变差，是请求根本发不出去。
- **工具结果必须紧跟在发起它的那条 assistant 消息后面。** 顺序错了，模型会看到「结果先于动作」，行为随之变形。

## 05 · 中间件全景

L4 长在循环外面，让模型可控地干完一件事。

你见过的所有 agent 能力——压缩记忆、卸载大输出、记录 trace、拦截危险命令、失败重试、验收打回——没有一个是新功能。它们全都是同一套钩子的不同用法。

### 钩子在哪

第 04 章那个 4 节点简化图，展开就是 8 个节点：

```
  before_agent ──────┐
                     ↓
  before_model → model_call → after_model ──┬→ before_tool → tool_call → after_tool ─┐
                     ↑                      └→ after_agent                                │
                     └──────────────────────────────────────────────────────────────────┘
```

沿圆环走一圈就是一轮：`before_agent` 开跑前进一次，`before_model` → `model_call` → `after_model`，需要动手就走 `before_tool` → `tool_call` → `after_tool`，然后回到 `before_model` 开始下一轮；不需要动手则由 `after_model` 直接交给 `after_agent` 收尾。中间件能插的位置，只有这 8 个。

钩子不是新节点，是两个节点之间那一瞬间。在它里面可以读 state、改 state，甚至决定不去下一个节点。

### 中间件 = (hook, handler)

handler 拿到 state，返回 state 或者一个跳转指令。后面六个中间件，全部落在这张表里。

| 中间件 | 挂在 | 解决什么 | 代价 |
| --- | --- | --- | --- |
| 上下文压缩 | before_model | 历史只增不减，第 30 轮 prompt 里全是废目录列表 | 摘要有损，细节丢了找不回 |
| 工具卸载 | after_tool | 一次 `ls -R` 把几万行灌进上下文 | 模型要多花一次调用读回全文 |
| 可观测 | 全部 | 出问题时你不知道它当时看到了什么 | 日志占存储，脱敏要额外做 |
| 人工审批 | before_tool | 模型直接生成 `rm -rf`，框架照单执行 | 每次打断有人工成本，会劝退高频场景 |
| model retry | after_model | 429 / 超时 / 5xx 直接让整个 run 挂掉 | 重试会叠加上游负载，需要退避与抖动 |
| evaluator | after_agent | 模型说「做完了」，其实只做了一半 | 多一次判定调用；判错会无限打回 |

为什么这件事值得单独讲：同一套钩子换个用法就能长出一种能力，所以中间件不是六个功能，是六个用法。真正的设计问题不是「要不要做某个能力」，而是「这个能力该挂在哪一瞬间」。

## 06 · 记忆：压缩与卸载

第 04 章那个循环有两个绕不过去的事实：历史只增不减，工具输出没有上限。两者叠加，到第三十轮时 prompt 里已积累数万 token 的无效目录列表。这一章讲两条处理路径：压缩历史，卸载工具输出。

### 压缩：一次真实的重写

第 12 轮，上下文 41,200 token，窗口预算 32,000。模型还没被调用，这一轮已经注定发不出去。

压缩中间件在 `before_model` 接管：挑 turn 3–9 的 14 条消息交给小模型做摘要。区间选择有讲究——system、首条 user 需求、最近 3 轮必须原样保留，只能压中间那段「已经用完、但还占着位置」的历史。

摘要回来：14 条变 1 条，用 4,200 token 换掉原来的 28,000，上下文从 41,200 降到 12,930。`messages` 数组被就地改写，那 14 条真的没了，而 system 与开头那条 user 需求仍留在原位。

模型收到的就是这个压缩版，它并没有「发现」历史被压缩过。省下的 28,270 token 就是这一轮实打实的成本。

### 压缩不能压什么

摘要不是「把历史变短」，是在有限预算下保住模型做决定所需的最小信息集。

| 必须保留 | 压了会怎样 |
| --- | --- |
| system prompt 与首条需求 | 前者含工具定义，后者是这次任务的目标。剔除工具定义模型不再知道自己有哪些工具；丢掉首条需求，后面所有判断都失去依据 |
| 最近 N 轮 | 当前这一步的判断依据全在这里。压缩后模型会丢失刚刚读取到的内容 |
| tool_call_id 配对 | 每一条 tool 消息都要对应一条 assistant.tool_calls。配对被破坏，请求直接返回 400 |
| 失败过的路径 | 「这条路试过，报错 xxx」是模型避免重复尝试的唯一依据。缺失这一条，模型会在第 14 轮再执行同一条命令 |

摘要本身还要调一次模型。压缩频率太高（比如每轮都压），付出的是「压缩调用 + 原始历史」两份成本。实践中通常只在超过阈值时压一次，压到 40% 左右，给后面留出增长空间。

### 卸载：按位置裁，按字节存

工具输出是另一回事：它单条就可能超阈值。`read_file` 返回 18,400 字符，其中约 17,000 字符是依赖下载的进度行。

做法是保留开头 400 字符（给上下文）、末尾 2,000 字符（结论在这里），中间 16,000 字符写成 `result_c7.txt` 落到磁盘，并插入一句「如需完整内容请加载」。上下文从 19,380 降到 3,382。

为什么保留末尾而不是开头：`build.log`、`pytest`、`npm install` 这类输出，结论永远在最后——前面几万行是依赖树和进度条，最后十行才是 `ERROR / FAILED / exit code`。裁掉开头、保留末尾，模型通常不需要读回全文就能判断；裁掉末尾、保留开头，等于把最有用的部分扔掉，模型会立刻再调一次工具读回，白花一次往返。

裁剪不是丢弃，是换页。全文必须还在某个地方，否则模型一旦真的需要中间那段，就永久失去了。

### 两条路径对应同一套机制

操作系统早已在用类似的分工：

| 操作系统 | 对应到 agent | 触发条件 | 回退手段 |
| --- | --- | --- | --- |
| 精度截断 | 上下文压缩 | token 超预算 | 摘要只保留粗粒度事实（原始细节不可还原） |
| 换页到磁盘 | 工具输出卸载 | 单条消息超阈值 | 按 `result_<id>.txt` 读回（无损） |
| 按需调入 | 长期记忆检索 | 新会话开始 / 相关度命中 | 向量召回 top-k 注入 |

区别在于可逆性：卸载能无损读回，压缩不能。缓存逐出不算这一类——被淘汰的页还能重新读回来，信息并没有真的消失。

### 完整的记忆系统

压缩和卸载只解决「装不下」。真实产品里还有第三个问题：该记的没记住。用户上周说过「我们只用 Python 3.11」，这周开新会话，agent 一无所知。

| 层 | 存在哪 | 存什么 | 怎么取回 | 谁负责写 |
| --- | --- | --- | --- | --- |
| 短期记忆 | checkpointer 里的 messages；state / scratchpad | 最近 N 轮与当前任务；计划、待办、已确认的事实 | messages 直接进 prompt；state 每轮注入 system 末尾 | 循环自动追加；中间件读写 |
| 长期记忆 | 向量库 + 图 | 跨会话偏好、项目知识、失败教训 | 检索 top-k 注入 | 写入前要抽取、去重、合并 |
| 归档 | 对象存储 / 文件 | 原始日志、完整工具输出、trace | 按 id 按需加载 | 卸载 / 可观测中间件 |

长期记忆真正的难点不在检索，在写入。写少了没用，写多了会污染：同一个偏好记了五条、三条互相矛盾、一条早已过期。所以成熟的记忆系统都有一套后台流程：抽取候选、去重合并、按时间衰减、定期清理。

一条实践顺序：先做卸载，再做压缩，最后才做长期记忆。前两个是确定性的、可测的（省了多少 token 一眼能看到）；长期记忆是概率性的，做早了只会得到一堆检索噪音。

## 07 · 可观测中间件

它挂在每一个节点上——这是六个中间件里唯一一个全节点的。因为它要回答的不是「怎么改行为」，而是「刚才到底发生了什么」。

### 一次运行的时间去哪了

还是前面的案例：5 轮模型调用、4 轮工具往返，总耗时 12.6 秒。完整的 span 记录是一棵树：

```
agent.run                         12,560ms   ← 根 span，before_agent 开、after_agent 关
├─ llm.turn1                       1,980ms   model=claude-sonnet  in=1,180 out=142
├─ tool.list_dir                     230ms   /repo  exit=0  bytes=48
├─ llm.turn2                       2,200ms   in=1,486 out=168
├─ tool.read_file                    170ms   requirements.txt  bytes=132
├─ tool.search_cve                   480ms   q=django  results=1
├─ llm.turn3                       2,200ms   in=1,690 out=205
├─ llm.turn4                       1,400ms   in=2,140 out=96
├─ tool.fanout                       500ms   ← 父 span，三个并行子 span
│  ├─ tool.read_file(app.py)         210ms
│  ├─ tool.read_file(README.md)       90ms
│  └─ tool.search_cve(requests)      500ms   ← 取最长的那条
└─ llm.turn5                       2,600ms   in=2,448 out=312   finish=stop
```

这张树最重要的结论：12.6 秒里有 11.2 秒在等模型，只有 1.4 秒在跑工具。所以「优化 agent 速度」最有效的手段，几乎从来不是换更快的工具或加缓存，而是减少轮次——每少一轮 model_call，就省掉 2 秒左右，顺便省掉一整段重放的 token。

注意 `tool.fanout` 这一层。并行调用在时间线上不是一条横条，是一组并排的条，父 span 的宽度取最长的那条。只记总耗时，会以为三个工具是串行跑的，性能账全算错。

### token 账本

| 轮次 | 输入 token | 输出 token | 这一轮干了什么 | 备注 |
| --- | --- | --- | --- | --- |
| turn 1 | 1,180 | 142 | 决定先看目录 | — |
| turn 2 | 1,486 | 168 | 读依赖 + 查 CVE | 新增 2 条工具消息 |
| turn 3 | 1,690 | 205 | 确认漏洞影响范围 | — |
| turn 4 | 2,140 | 96 | 并行读三个文件 | 一次发 3 个 tool_call |
| turn 5 | 2,448 | 312 | 产出补丁建议 | `finish=stop` |
| 合计 | 8,944 | 724 | 9,668 token | — |

### 记什么

| 字段 | 为什么记 |
| --- | --- |
| 完整 prompt | 复现「它当时到底看到了什么」的唯一办法 |
| tool 参数 | 判断危险调用、排查参数错误 |
| tool 输出大小 | 发现「上下文被撑爆」的源头 |
| TTFT | 首 token 延迟直接决定体感速度；和总耗时分开记，两者不是一回事 |
| finish_reason | 区分「正常结束」和「被截断」；截断要单独告警，它会悄悄丢答案 |

可观测本身是一个隐私面：完整 prompt 里可能含用户上传的文档、数据库字段、内部路径。trace 系统往往是整个 agent 里最容易造成数据外泄的一环——它把所有东西都抄了一份，还存很久。上线前要先定清楚：存多久、谁能读、哪些字段必须脱敏。

## 08 · 人工审批中间件

前面所有中间件都在改数据，只有这一个在改控制流：它能让循环停下来，等人说话。挂在 `before_tool`——因为它是最后一个「命令还没跑」的位置。

### 为什么必须挂在这里

| 挂载点 | 能看见什么 | 能不能阻止 |
| --- | --- | --- |
| before_model | 历史、目标 | 能阻止「调模型」，但拦不到具体命令——参数还没生成 |
| after_model | 即将调用的工具名与参数 | 能，但这里拦下等于丢弃模型的输出，语义不清（模型会以为自己发出去了） |
| before_tool | 工具名 + 完整参数 | 能，而且是唯一语义清晰的位置——拒绝就是这条命令没执行 |
| after_tool | 执行结果 | 不能。只能事后补偿（回滚、告警） |

`before_tool` 上的一次挂起是这样走的：

```
模型生成 tool_call
  → before_tool（handler 判定：需要人工）
  → 挂起，把「工具名 + 完整参数」推到审批队列
  → 人批准：继续执行 tool_call
  → 人拒绝：写回一条 tool 结果「用户不同意」，模型走降级路径
```

拒绝不能只回一句「不同意」。模型很可能原地重试同一条命令（它不知道为什么）。要把原因带上：「用户不同意执行 `rm -rf /var/cache/*`，理由是范围过大」——模型下一轮就会改成 `find -mtime +7`，这才是有效的反馈。

### 什么该拦

| 信号 | 看什么 | 典型规则 |
| --- | --- | --- |
| 命令动词 | 破坏性动作 | rm、dd、mkfs、DROP TABLE、truncate |
| 作用范围 | 有没有通配符 / 递归 / 绝对路径 | `*`、`-r`、`/**`、系统目录（/etc、/var、~/.ssh） |
| 外发方向 | 数据是否离开本机 | `curl -d @file`、scp、发邮件、写外部 API |
| 权限升级 | 是否要求更高权限 | sudo、chmod 777、改 SSH 配置 |
| 不可逆 | 有没有回退路径 | 删库、强推、覆盖未提交的工作区 |

规则要准，不要多。审批机制最大的敌人是疲劳：一个 agent 每次跑都弹三次确认，用户第三天就会无脑点「同意」，那时候审批层不但没保护你，还给了你虚假的安全感。

### 三种降级：不必每次都问人

**dry-run（先预演，不执行）：** 把命令换成只打印、不写盘的形式先跑一遍。`rsync -av` 加 `--dry-run` 只列会同步哪些文件；`git clean -f` 换成 `git clean -n` 只列会删哪些文件；`rm` 没有预演模式，就用 `find` 列出匹配路径。用户看完影响范围再决定，很多时候看完这一步就不需要批准了。

**改写后放行（批准的是改写版，不是原文）：** 不改意图，只把动作换成副作用可控的等价形式。三种常见做法：

- 换成可恢复版本：`rm -rf /var/cache/*` → 移到 `trash/cache/`，或 `find ... -mtime +7`；
- 收窄范围：`rm -rf /repo/*` → `rm -rf /repo/build/`；
- 加保护：`git push --force` → `git push --force-with-lease`。

模型拿到的结果是「做完了」，但破坏半径被压到一条命令就能恢复，因此不占一次人工确认。

**规则化分流：** 只读操作自动放行，可逆写操作走 dry-run 或改写，不可逆、跨边界、涉及外部系统的才强制人工。

### 审批记录

谁批的、什么时候、批的是哪条命令、当时看到的参数是什么。事后追责靠的不是日志搜索，是结构化的审批记录——审批事件本身就是一条 span，和工具调用、模型调用放在同一棵树上。

超时要按 fail-closed 处理：用户去开会，审批卡挂 10 分钟没人点，默认放行等于把闸门拆了。正确做法是超时即拒绝，让模型走「用户不同意」那条路径，任务降级但不闯祸。

## 09 · 控制流中间件

前五个中间件改的是数据、权限、记录。这一类改的是图本身：它不走「下一步」，而是往回跳。一个 agent 能不能自我纠正，就取决于有没有这条回边。

### ① 重试：失败也要有节奏

一次 `model_call` 返回 429。这一类是可重试的：4xx 里的限流、5xx、网络超时都可以重试；参数错误、内容审核拒绝不可重试。

重试不是原地立刻再发。失败的所有请求在同一毫秒重试，就是一次集中的流量峰值——上游刚恢复又被压垮，你也就永远重试不上。所以退避必须是指数 + 抖动：

```
attempt 1  失败 → 退避 1.2s（±随机抖动）→ jump 回 before_model
attempt 2  仍 429 → 说明上游是真的在限流，不是抖动 → 退避 2.4s
attempt 3  成功 → 继续
```

重试要有上限，并且上限到了要能交出控制权。重试本身也是一条回边，回边必须有人管住次数。

### ② 评审：在 after_agent 把结果打回去

目标是「找出所有带高危漏洞的包」，模型只修了 Django 和 requests 就宣布结束。`after_agent` 上的 judge 拿着最初那句 goal 去核对，发现漏了 pyyaml。

完整的回环是：模型宣称完成 → judge 判定 2/3 不通过 → feedback 写回 messages → jump 回 `before_model` → 调 `search_cve("pyyaml 5.4.1")` 拿到 CVE-2020-14343 → `model_call` 把工具结果并入结论 → judge 二次评审 3/3 通过 → `agent_end`。

工具返回之后必须有一步模型调用：judge 核对的是模型输出的结论，不是工具返回值。少了这一步，judge 手上没有可核对的对象。

feedback 怎么插：它不是一条新的 user 消息——那会看起来像用户改了需求。实际实现里通常是一条 `role:"judge"` 或 `role:"system"` 的批评，明确写出缺了什么、依据是什么：

```json
{ "role": "judge",
  "content": "goal 要求覆盖所有高危包。当前只处理了 2 个，
              pyyaml 的 CVE-2020-14343 未修复。请继续，不要重复已完成的。" }
```

judge 用什么判，取决于任务性质：

| judge 用什么判 | 适合 | 代价 |
| --- | --- | --- |
| 硬规则 | 有明确验收条件的：测试通过、文件存在、格式合法 | 最便宜最可靠，但只能查「能不能」，查不了「好不好」 |
| 另一个模型 + rubric | 开放式任务：报告、代码质量、需求覆盖度 | 多一次调用；judge 也会看走眼 |
| 人工 | 高风险交付 | 慢，但兜得住 |

评审必须设上限。judge 苛刻一点、模型改一点、judge 还不满意，这个环可以转到天荒地老。`max_evals` 是硬约束，到顶就交给人，或者带着「未完全达标」的标记退出。

### 六个中间件的收束

| 中间件 | 挂点 | 动作 | 闭环了什么 |
| --- | --- | --- | --- |
| 压缩 | before_model | 改 messages（少） | 上下文不会爆 |
| 卸载 | after_tool | 改 messages（换页） | 工具不会撑爆上下文 |
| 可观测 | 全部 | 只读，不改 | 出了问题能查、能算账 |
| 审批 | before_tool | 挂起，等人审批 | 危险动作有人兜底 |
| 重试 | after_model | jump 回 before_model | 瞬时失败不终止任务 |
| 评审 | after_agent | 插 feedback + jump 回 | 「声称完成」不等于完成 |

中间件是一切行为的闭环：可评测、可介入、可影响记忆、可观测、可容错。一个 agent 的能力上限由模型决定，但它的可靠性和可运维性，几乎完全由这一层决定。

## 10 · 流式与前端

前面九章都在讲 agent 内部怎么转。这一章讲它怎么把转的过程露出来——因为一个跑 40 秒、调了十几个工具的 agent，如果只是转圈等结果，用户唯一能做的事就是怀疑它卡死了。

| 场景 | 不流式 | 流式 |
| --- | --- | --- |
| 一次 8 秒的回答 | 转圈 8 秒，然后一次性出现 | 第 0.4 秒就开始出字，8 秒时结束 |
| 一个 40 秒、12 次工具的任务 | 转圈 40 秒，用户会以为卡死然后刷新 | 能看到「正在读 app.py」「正在查 CVE」，知道它没停 |
| 命令跑错了 | 跑完才看到结果，已经写进库了 | 参数一出现就能看出不对，来得及中断 |
| 模型开始胡说 | 只能等它说完 | 第一句话就能点停止，省下剩余 token |

### 流的粒度

按 token 流太碎（一屏几十次重排），按整块流又回到转圈。正确做法是按事件流，在事件内部按 delta 流：界面结构的变更走事件（粗粒度、可预测），文本内容的增长走 delta（细粒度、可合并）。

| 事件 | 来源 | 前端该做什么 |
| --- | --- | --- |
| agent_start | before_agent | 清空上一次的界面，进入「运行中」，开计时器 |
| llm_start | model_call 前 | 创建助手气泡（空的，带光标） |
| llm_delta | 模型流式输出 | 追加字符到气泡，不要重绘整条消息 |
| llm_end | model_call 后 | 去掉光标，用 `llm_content` 校正全文 |
| tool_start | before_tool 后 | 创建工具卡片 / 终端框 |
| tool_args | 参数就绪 | 把参数填进框里，例如 `$ ping www.huawei.com` |
| tool_delta | 工具运行中 | 追加输出。注意它可能是字节流，不按行对齐 |
| tool_end | after_tool 前 | 框闭合、显示 exit code、停光标，用 `tool_content` 校正全文 |
| agent_end | after_agent | 收口、汇总耗时与 token |

delta 拼出来的文本，不一定是最终文本。模型可能被截断、被过滤，工具输出也可能乱序。所以协议里要有 `llm_content` / `tool_content` 这类事件，随结束事件一起带上完整结果；前端以它为准，delta 只用于过程中的实时渲染。只信 delta 的实现，会在长回答上偶发地少字、重复字——而且极难复现。

### 一轮完整的事件顺序

```
agent_start
  llm_start → llm_delta … → llm_end
  tool_start → tool_args → tool_delta … → tool_end
  llm_start → llm_delta … → llm_end        ← 工具结果必须回到模型
  agent_end
```

终端闭合之后，界面还在等模型给结论，然后才进 done。这一段等待是必要的，不是卡顿。

### 取消

用户点「停止」时，要能真的停下来——不只是关掉前端的订阅，还要让后端的 `model_call` 和 `tool_call` 收到中断信号。只关前端不关后端，是最常见的「假停止」：界面停了，token 还在烧。

## 11 · 决策：把「选一个」从生成里拆出来

agent 每转一圈，真正要回答的问题只有几类：下一步调哪个工具、这条命令要不要批、这次算不算做完。语言模型也能回答，但它的方式是写一段话出来——写 JSON，再解析。

决策模型把这件事件换成另一种形式：给候选打分，选最高分。它不做自回归生成，一次前向就能并发给多个候选打分，因此快、省资源，也没有 JSON 解析失败的风险。

同一件事交给语言模型，框架要拿到 `{"tool":"read_logs","args":{...}}` 再解析；交给决策模型，拿到的是几个数：

| 候选 | 分数 |
| --- | --- |
| read_logs | 0.94 |
| grep_error | 0.88 |
| run_shell | 0.41 |
| delete_logs | 0.07 |

差别不在聪明程度，在输出形态。

### 第二个落点：把审批从「每次问人」变成「按分数分流」

人工审批的瓶颈不是判断难，是次数多。既然决策模型能输出概率，就让它先给一个分，再按阈值分流：高分直接放行，中间分段交给人，低分直接拒绝。

- 分数 ≥ 0.80：自动放行；
- 0.50 ≤ 分数 < 0.80：人工审批；
- 分数 < 0.50：直接拒绝。

阈值抬得越高，交给人看的越多，安全性上升、效率下降；压得越低，放行越多，漏放危险动作的概率也随之上升。阈值不该拍脑袋定，应该拿真实审批记录去校准——被人工否掉的那些样本，分数本来应该落在哪个区间。

### 它替代不了什么

- 它不生成内容。决策模型回答的是「从这几个里选哪个」「要不要」，它写不出日志摘要，也写不出补丁。生成那一段仍然由语言模型做。
- 候选集合要先给全。它是在给定候选上打分，不是凭空空想。工具清单、审批策略、路由分支必须显式枚举——漏掉的候选，它永远选不到。
- 分数要能解释。一个 0.83 的放行分，事后追责时需要知道它凭什么。决策这一步要进 trace，和工具调用、审批记录放在一起看。

### 放回循环里看

决策模型不是挂在某一处，它可以挂在循环里的任何一个节点上——每个节点都对应一个「要不要、选哪个、算不算」的问题。模型调用和工具执行本身不是决策，它们是被判断的对象。

| 节点 | 那一处要判什么 |
| --- | --- |
| before_agent | 这段输入能不能收：是不是提示词覆盖、有没有夹带越权指令、意图是否清楚到可以开工。判不过就直接拒掉，不必先烧一次模型调用 |
| before_model | 这份上下文够不够、贵不贵：要不要压缩、哪几段可以合并、需不需要先检索一段补进来 |
| model_call | 生成，不是决策。它上游「用哪个模型、给多少预算」仍是一次选择，只是发生在调用之前 |
| after_model | 这段输出能不能用：是不是空的、前后是否矛盾、要不要重试；以及这一次继续调工具还是可以收尾 |
| before_tool | 这条命令放不放：给一个概率，高分放行、中间给人、低分拒掉；顺带判参数是否越界、是不是只读操作 |
| tool_call | 执行，同样不是决策。它能被判断的地方在外面：跑太久要不要中断、输出是否已经够用 |
| after_tool | 这份结果值不值得往下走：是不是空、是不是报错、要不要重试或转人工；以及直接回灌还是先裁剪加工 |
| after_agent | 事情真的做完了吗：拿最初目标给结果打分，够了就结束，不够就把 feedback 打回去 |

同一套打分机制，换一个训练目标就能挂在不同的位置上。这也是它的价值所在：agent 里「选一个」的判断到处都是，而这些判断并不需要语言模型来写。

## 结语

把这条链收起来：LLM 提供能力，工具提供触达，循环把两者接成行动，中间件把行动变得可控可查，流式把可控可查变成用户能看见的东西。

四层结构、六个中间件、八个钩子、一套事件流。换任何一个框架，名字会变，位置不会变：模型调用、工具执行、把两者串起来的循环，以及围在循环外面的那一圈拦截层。
