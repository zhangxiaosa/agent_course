06 / MEMORY

记忆：压缩与卸载

第 04 章那个循环有两个绕不过去的事实：历史只增不减，工具输出没有上限。这两件事撞在一起，第三十轮的 prompt 里会躺着几万 token 的废目录列表。这一章讲两条止血带。它们其实是同一件事——给 agent 做虚拟内存。

① 上下文压缩 · 挂在 before_model

before_model 命中
checkpoint
messages 记录
READY 第 12 轮的 agent 已经把上下文堆到 41,200 token，而窗口预算只有 32,000。点「下一步」，看压缩在这一轮里怎么动手。

压缩不能压什么

这是最容易踩坑的地方。摘要不是"把历史变短"，是在有限预算下保住模型做决定所需的最小信息集。四条硬规则：

必须保留压了会怎样
system prompt里面有工具定义。压掉 = 模型不知道自己有什么工具，下一轮直接不调了。
最近 N 轮当前这一步的判断依据全在这儿。压掉 = 它忘了刚才刚看到什么。
tool_call_id 配对每一条 tool 消息都要对应一条 assistant.tool_calls。压断配对，请求直接 400——不是效果变差，是根本发不出去。
失败过的路径「这条路试过，报错 xxx」是模型避免重复踩坑的唯一依据。压掉它，它会在第 14 轮再试一次同样的命令。
摘要的隐性成本：压缩本身要调一次模型。如果压缩频率太高（比如每轮都压），你付出的是"压缩调用 + 原始历史"两份成本，换来的只是更短的上下文。实践中通常只在超过阈值时压一次，压到 40% 左右，给后面留出增长空间。

② 工具输出卸载 · 挂在 after_tool

after_tool 命中
checkpoint
messages 记录
READY 这次换一个方向：不是历史太长，是单条消息太长。模型读一个构建日志，工具一口气返回了 18,400 个字符。

为什么留头留尾，只裁中间

工具输出的信息密度是不均匀的。build.log、pytest、npm install 这类输出，开头几行是命令回显、文件路径、版本号，中间几万行是依赖树和进度条——重复、可预测、几乎不含判断所需的信息，最后十来行才是 ERROR / FAILED / exit code 和结论。

所以要裁的是中间。只留末尾，模型不知道这段输出来自哪个文件、跑了什么命令，结论缺了上下文；只留开头，等于把结论扔掉，模型会立刻再调一次工具读回，白花一次往返。头 400 + 尾 2,000 是折中：定位信息和结论都在手上，中间那 16,000 字符落盘待查。

after_tool 的裁剪逻辑（示意）

if (output.length <= LIMIT) return output;

const head = output.slice(0, 400);           // 保留开头，给上下文
const tail = output.slice(-2000);            // 保留末尾，结论在这
const dropped = output.length - head.length - tail.length;

const note = `\n\n[已省略 ${dropped} 个字符。`
           + `如需完整内容，请加载 result_${toolCallId}.txt]`;

saveToFile(`result_${toolCallId}.txt`, output);   // 全文落盘
return head + note + tail;

注意 saveToFile 这一步：裁剪不是丢弃，是换页。全文必须还在某个地方，否则模型一旦真的需要中间那段，就永久失去了。

这两件事其实是虚拟内存

把两个中间件放在一起看，会发现它们在做操作系统几十年前就做过的事：

操作系统对应到 agent触发条件回退手段
缺页换出上下文压缩token 超预算摘要里保留关键事实（不可逆，有损）
换页到磁盘工具输出卸载单条消息超阈值按 result_<id>.txt 读回（无损）
缓存长期记忆检索新会话开始 / 相关度命中向量召回 top-k 注入
日志归档完整 trace 落盘run 结束按 trace_id 回放

差别在于：操作系统的缺页是硬件强制的，agent 的缺页是你自己判断的。判断错了，换来的是"模型忘了关键约束"或者"模型反复读同一个文件"——这两种症状在线上都表现为"这 agent 怎么突然变笨了"，而根因在中间件的阈值上。

再往前一步：完整的记忆系统长什么样

压缩和卸载只解决"装不下"。真实产品里还有第三个问题：该记的没记住。用户上周说过"我们只用 Python 3.11"，这周开新会话，agent 一无所知。这就需要一个真正的记忆层。

层存在哪存什么怎么取回谁负责写
上下文窗口内存（messages）最近 N 轮、当前任务直接进 prompt循环自动追加
工作记忆state / scratchpad计划、待办、已确认的事实每轮注入到 system 末尾中间件读写
长期记忆向量库 + 图跨会话偏好、项目知识、失败教训检索 top-k 注入写入前要抽取、去重、合并
归档对象存储 / 文件原始日志、完整工具输出、trace按 id 按需加载卸载 / 可观测中间件

长期记忆真正的难点不在检索，在写入。写少了没用，写多了会污染：同一个偏好记了五条、三条互相矛盾、一条早就过期。所以成熟的记忆系统一定有一套后台流程：

  • 抽取——从对话里判断"这句话是一条值得长期记住的事实吗"，而不是把整段对话倒进向量库。
  • 去重与合并——新事实和已有条目语义相近时，选择更新旧条目而不是新增一条。
  • 遗忘——带时间衰减；被引用得少的条目降权，长期不用就归档。
  • 接管——冲突时以最新为准，并把旧结论标记为"已被推翻"，而不是删掉（模型需要知道"曾经以为是这样"）。
一条经验：先做卸载，再做压缩，最后才做长期记忆。前两个是确定性的、可测的（省了多少 token 一眼能看到）；长期记忆是概率性的，做早了只会得到一堆检索噪音。
