05 / MIDDLEWARE

中间件全景

你见过的所有"agent 能力"——压缩记忆、卸载大输出、记录 trace、拦截危险命令、失败重试、验收打回——没有一个是新功能。它们全都是同一套钩子的不同用法。

钩子在哪

第 04 章的 4 节点简化图，展开就是下面这 8 个节点。蓝 是模型侧，青 是工具侧，琥珀 是钩子。钩子不是新节点，是"两个节点之间那一瞬间"——在它里面你可以读 state、改 state、甚至决定不去下一个节点。

agent 生命周期 · 8 个钩子

自上而下、再自下而上，走完一圈就是一轮。左边那条竖线是回环：after_tool 走完，回到 before_model，下一轮开始。中间件能插的位置，只有这 8 个。

六个中间件 × 八个钩子

纵向是时间，横向是六个中间件。点任意一格，看它在那一个瞬间具体做什么。空格也点了会告诉你为什么那里不能挂。

为什么这件事值得单独讲

因为它是唯一一处可以不改模型、不改工具、不改循环，只加代码就能改变 agent 行为的地方。想让它记得更久，不用换模型，在 before_model 加压缩；想让它不出事故，不用改 prompt，在 before_tool 加审批；想让它别在半路停下，不用重训，在 after_agent 加验收。

反过来说，如果你要做的事没法表达成"某个钩子上的一个函数"，那它就不是中间件，而是循环本身的一部分——你就得改图。

一句话记住：中间件 = (hook, handler)。handler 拿到 state，返回 state 或者一个跳转指令。没有第九种原语。第 06–09 章讲的六个中间件，全部落在这张表里。

这六个各自解决什么问题

中间件挂在解决什么代价
上下文压缩before_model历史只增不减，第 30 轮 prompt 里全是废目录列表摘要有损，细节丢了就找不回
工具卸载after_tool一次 ls -R 把几万行灌进上下文模型要多花一次调用来读回全文
可观测全部出问题时你不知道它当时看到了什么日志本身占存储，脱敏要额外做
人工审批before_tool模型直接生成 rm -rf，框架照单执行每次打断都有人工成本，会劝退高频场景
model retryafter_model429 / 超时 / 5xx 直接让整个 run 挂掉重试放大会把上游打得更惨，必须退避
evaluatorafter_agent模型说"做完了"，其实只做了一半多一次判定调用；判定错了会无限打回

注意每一行的"代价"都不是零。中间件不是免费的开关，是用一种成本换另一种成本——这也是为什么真实的 agent 系统里通常只开其中三四个，而不是六个全开。
