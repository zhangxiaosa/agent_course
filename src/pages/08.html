08 / APPROVAL

人工审批中间件

前面所有中间件都在"改数据"，只有这一个在改控制流：它能让循环停下来，等人说话。挂在 before_tool——因为它是最后一个"命令还没跑"的位置。

先看一个具体的危险

任务很普通：/var 快满了，让 agent 清一下。它很合理地选了这条命令。下面的演示走到 before_tool 时会真的挂起，你来点同意或拒绝，两条路会走到完全不同的结局。

before_tool · 闸门
checkpoint
messages 记录
READY agent 收到任务："/var 快满了，清一下缓存"。点「下一步」看它选了哪条命令。

为什么必须卡在 before_tool

因为中间件能"看见"参数的最早时刻，和能"阻止执行"的最晚时刻，都在这一点。再往前（before_model），参数还没生成，你不知道要拦什么；再往后（after_tool），命令已经跑完了，你只能追认。

挂载点能看见什么能不能阻止
before_model历史、目标能阻止"调模型"，但拦不到具体命令——参数还没生成
after_model即将调用的工具名与参数能，但这里拦下等于丢弃模型的输出，语义不清（模型会以为自己发出去了）
before_tool工具名 + 完整参数能，而且是唯一语义清晰的位置——拒绝就是"这条命令没执行"
after_tool执行结果不能。只能事后补偿（回滚、告警）

规则怎么写

"危险"不是一个字符串匹配能解决的。rm -rf 很危险，但 rm -rf ./build 是日常工作；git push 看起来无害，但 --force 到 main 是灾难。实际系统里通常是几个信号叠加：

信号看什么典型规则
命令动词破坏性动作rm、dd、mkfs、DROP TABLE、truncate
作用范围有没有通配符 / 递归 / 绝对路径*、-r、/**、系统目录（/etc、/var、~/.ssh）
外发方向数据是否离开本机curl -d @file、scp、发邮件、写外部 API
权限升级是否要求更高权限sudo、chmod 777、改 SSH 配置
不可逆有没有回退路径删库、强推、覆盖未提交的工作区

规则命中后有三种结局，不止两种：

  • 放行——用户点了同意，工具照原参数执行。
  • 拒绝——工具不执行，但依然往 messages 里写一条 role:"tool" 的结果："用户不同意执行"。模型收到的是一个事实，不是一个错误。
  • 改写后放行——把 rm -rf /var/cache/* 改成 find /var/cache -type f -mtime +7 -delete，让用户确认新命令。这是最实用的一种：多数时候用户不是要拒绝，是要改得更保守。
审批机制最大的敌人是疲劳。一个 agent 每次跑都弹三次确认，用户第三天就会无脑点"同意"——那时候审批层不但没保护你，还给了你虚假的安全感。规则要准，不要多：只拦真正不可逆的，剩下的用"改写后放行"或 dry-run 兜住。

三个容易做错的地方

① 超时默认怎么处理。用户去开会了，审批卡挂了 10 分钟没人点。默认放行等于把闸门拆了；正确做法是 fail-closed——超时即拒绝，让模型走"用户不同意"那条路径，任务降级但不闯祸。

② 拒绝要给模型留退路。只回一句"不同意"，模型很可能原地重试同一条命令（它不知道为什么）。把原因带上："用户不同意执行 rm -rf /var/cache/*，理由是范围过大"——模型下一轮就会换 find -mtime，这正是上面演示里发生的事。

③ 审批要留审计。谁批的、什么时候、批的是哪条命令、当时看到的参数是什么。事后追责靠的不是日志搜索，是结构化的审批记录。这一条和第 07 章的可观测是同一套东西：审批事件本身就是一个 span。
