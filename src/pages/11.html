11 / DECISION

决策：把「选一个」从生成里拆出来

agent 每转一圈，真正要回答的问题只有几类：下一步调哪个工具、这条命令要不要批、这次算不算做完。语言模型也能回答，但它回答的方式是"写一段话出来"——写 JSON，再解析。决策模型把这件事件换成另一种形式：给候选打分，选最高分。

用生成做决策，代价在哪

语言模型输出的是 token 序列。哪怕结果只是一个工具名，它也要一个一个 token 写出来：先写 {"tool":，再写工具名，再写参数。这带来三笔开销。

  • 时延跟着输出长度走。自回归只能逐 token 解码，JSON 越长，等得越久。决策本身只是"选哪个"，却被迫付出一整段文本的生成成本。
  • 结果要解析。模型吐出的是文本，框架要 JSON.parse 一次。字段写错、引号缺失、多写一句话——整轮调用直接失败，得重试或降级。
  • 候选多了只能串行问。四个候选工具就是四次生成，或者一次生成里塞四个分支；前者慢，后者更容易写错。

决策模型把这三个问题一起绕开。它不是自回归的：不逐个 token 解码，而是把上下文和候选集合一起编码，一次前向给每个候选算一个分。候选之间互不依赖，可以并发，输出也不是文本，而是分数或概率——不存在"解析失败"这一步。

两个落点：选工具，和要不要批

下面这块就是一个最典型的工具选择：上下文进来，四个候选动作各打一个分，最高分被选中。整个过程只有一次前向，没有生成任何 token。

context · 用户说「把线上日志里的 ERROR 汇总一下，别动源文件」。可用工具见下方候选。
待打分

同一件事交给语言模型，框架要拿到一段形如 {"tool":"read_logs","args":{...}} 的文本再解析；交给决策模型，拿到的是 四个数。前者生成几十个 token，后者一次前向——差别不在聪明程度，在输出形态。

第二个落点：把审批从"每次问人"变成"按分数分流"

人工审批的瓶颈不是判断难，是次数多。每条命令都弹窗，用户第三天就会无脑点同意。既然决策模型能输出概率，就让它先给一个分，再按阈值分流：高分直接放行，中间分段交给人，低分直接拒绝。人只看真正模糊的那一段。

拖动两根阈值就能看出这套机制的取舍：阈值抬得越高，交给人看的越多，安全性上升、效率下降；压得越低，放行越多，漏放危险动作的概率也随之上升。阈值不该拍脑袋定，应该拿真实审批记录去校准——被人工否掉的那些样本，分数本来应该落在哪个区间。

它替代不了什么

  • 它不生成内容。decision 模型回答的是"从这几个里选哪个"、"要不要"，它写不出日志摘要、写不出补丁。生成那一段仍然由语言模型做。
  • 候选集合要先给全。它是在给定候选上打分，不是凭空空想。工具清单、审批策略、路由分支必须显式枚举出来——漏掉的候选，它永远选不到。
  • 分数要能解释。一个 0.83 的放行分，事后追责时需要知道它凭什么。决策这一步要进 trace，和工具调用、审批记录放在一起看。

放回循环里看

决策模型不是挂在某一处，它可以挂在循环里的任何一个节点上——每个节点都对应一个「要不要、选哪个、算不算」的问题。区别只在于同一时间扣的是哪一道闸。下面这张图的每个节点都可以点，点开看那一处能做什么判断。
