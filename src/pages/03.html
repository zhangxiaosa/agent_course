03 / TOPOLOGY

Agent 的形态谱系

同样的模型、同样的工具，换个拓扑就能解决完全不同的问题。形态不是风格选择，是成本与可控性的权衡——越自由的结构越能处理未知路径，也越难预测它下一步会干什么。

五种形态，按"自由度从低到高"排：CoT 是一条线，ToT 是一棵树，Plan-and-Execute 是两段，工作流是一张人写死的图，ReAct 是一个环。点上面的标签逐个看，每个都给了一个能上手玩的示意。

问题 步骤 1拆解 步骤 2代入 结论
每步输出 → 下一步输入 · 单向
一条直线，没有岔路每一步的输出直接成为下一步的输入。错了没有回头路——想改只能从头再来。
怎么工作一次调用里让它先写步骤、再给结论（CoT prompting）；或工程上拆成串行多次调用，上一步输出当下一步输入。你说的"多调几次 llm 逼它思考"，是后者。
什么时候用路径唯一、不需要外部信息、步骤可预见。算术、格式转换、单文档摘要。
代价一条路走到黑。步骤一长，前后会自相矛盾，而且没有任何机制能发现它错了。
点上面任意一个思路，展开它的下一步把"下一步"变成"多个下一步"：每个分支独立评估，高的留、低的剪，全死了就回溯上一层换路子。试试点三个分支看看。
怎么工作生成 N 个候选 → 让评估器打分 → 保留 top-k → 对每个保留项继续展开 → 全部分支剪光时回溯到上一层。
什么时候用搜索式问题：性能调优、定理证明、方案比选。答案是"试出来的"而不是"想出来的"那些。
代价调用次数 = 分支数 × 深度。深度 3、每层 3 个分支就是 27 次调用。而且你要有个靠得住的评估器，否则剪枝就是瞎剪。
PLANNER · 一次调用出完整计划
EXECUTOR · 逐条执行，不回看计划
先冻结，再执行计划和执行被拆成两个阶段。好处是计划可以给人看、可以中途停、可以换个执行器跑；坏处是它在第一步之前就定死了。
怎么工作Planner 出一份带依赖的步骤清单 → Executor 按序跑，每步把结果记下来 → 全部跑完后 Replanner 决定收尾还是补一步。
什么时候用步骤可预先枚举、需要人审、需要中断续跑的长任务。研究报告、批量数据处理。
代价真实世界会在第 3 步给你一个计划里没写过的东西。此时要么硬着头皮跑完（结果错），要么整份重规划（钱白花）。

点节点看它干什么路由一个查询，三个检索并发跑，结果在 merge 汇合。图是人写的，所以可复现、可审计、可加边——代价是遇到图上没有的情况它不会自己想办法。
怎么工作节点是 LLM 调用、工具调用或一个判断；边是数据流。分支、并发、汇总都是图的属性，不是模型的自由发挥。
什么时候用流程稳定、要求结果一致、要给别人看流程图当交付物。客服工单、内容审核、数据管线。
代价覆盖不到的情况只能靠人加边。图越大越难维护，最后往往退化成"半个 agent"。
model_call tool_call messages += result
↺ 回到 model_call · 直到 finish_reason = stop
没有图，只有循环下一步做什么，由模型看着历史自己决定。2022-10 的 ReAct 论文，今天成了绝大多数 coding agent 的骨架，因为编码任务的路径本来就不可预知。完整回放见下一章。
怎么工作model_call 产出工具参数 → tool_call 执行 → 结果追加进 messages → 再调模型，整段历史全量重放。
什么时候用路径不可预知、需要边做边看。Coding、运维排查、网页操作。agentic RL 训练的也正是这个环。
代价上下文只增不减、参数直接进执行器、完成与否由模型自己说。三个病，第 05 章开始逐个治。

形态拓扑调用次数可预见性典型场景
CoT直线1 ~ n 串行高推理、格式转换
ToT树，可回溯分支 × 深度中调优、方案比选
Plan-and-Execute两段式1 + n高（计划冻结）长任务、需人审
工作流 DAG图，人写死节点数最高稳定流程、要审计
ReAct环不定，受上限约束最低Coding、开放任务

注意这张表里没有"最好"的一列。可预见性和能力是反向的：图越死，你越能保证它不闯祸，也越不能指望它解决图外的问题。真实系统常常混着用——外层是 DAG（保证流程），每个节点里塞一个 ReAct 环（处理节点内的不确定性）。
