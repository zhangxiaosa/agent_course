为什么 agent 比聊天更需要流式



普通聊天里，流式是体验优化：早几百毫秒看到字，感觉更快。agent 不是——agent 的流式是可信度的来源。






  
  
场景不流式流式

  
    
一次 8 秒的回答转圈 8 秒，然后一次性出现第 0.4 秒就开始出字，8 秒时结束

    
一个 40 秒、12 次工具的任务转圈 40 秒。用户会以为卡死，然后刷新能看到"正在读 app.py""正在查 CVE"，知道它没停

    
命令跑错了跑完才看到结果，已经写进库了参数一出现就能看出不对，来得及中断

    
模型开始胡说只能等它说完第一句话就能点停止，省下剩余 token

  






所以流式的价值不在"快"，在"可见"：把黑箱拆成一段段可观察的过程。这也是第 07 章可观测的前端投影——后端记 span，前端放事件，同一个东西的两种呈现。



事件怎么定义



后端每发生一件事，就吐一个带类型的事件。粒度要够细，前端才能分别处理：






  
  
事件来源前端该做什么

  
    
agent_startbefore_agent清空上一次的界面，进入"运行中"，开计时器

    
llm_startmodel_call 前创建助手气泡（空的，带光标）

    
llm_delta模型流式输出追加字符到气泡。不要重绘整条消息

    
llm_endmodel_call 后去掉光标，用 final 字段校正全文

    
tool_startbefore_tool 后创建工具卡片 / 终端框

    
tool_args参数就绪把参数填进框里，例如 $ ping www.huawei.com

    
tool_delta工具运行中追加输出。注意它可能是字节流，不按行对齐

    
tool_endafter_tool 前框闭合、显示 exit code、停光标

    
agent_endafter_agent收口、汇总耗时与 token

  






为什么 llm_start 和 llm_delta 要分开？因为第一个 delta 可能要等零点几秒（TTFT）。这段时间前端需要先有一个"正在说话"的空气泡——否则用户看到的还是转圈，前面做的功夫全白费。



线上跑的是 SSE



前后端之间绝大多数用 SSE（Server-Sent Events），不是 WebSocket。原因很简单：这是单向推送，SSE 就是 HTTP 上的一个长连接，不需要协议升级、能穿过大多数代理、断了浏览器会自动重连。



event: llm_delta
data: {"seq":17,"text":"先测一下到 "}

event: tool_start
data: {"seq":24,"tool":"shell","id":"call_a3f"}

event: tool_delta
data: {"seq":28,"stream":"stdout","text":"64 bytes from 121.36.158.11"}



三个细节值得注意：



    
  
  • seq 必须单调递增。前端的追加逻辑要幂等：收到比当前小的 seq 直接丢弃。没有这个字段，重连之后你会看到重复的字。
    • 
  
  • event: 是类型，前端用 addEventListener('llm_delta', ...) 按类型注册处理器，而不是在回调里写一长串 if/else。
    • 
  
  • 断线靠 Last-Event-ID 续传。浏览器重连时自动带上最后收到的事件 id，服务端从那一条之后接着发。没有这个机制，长任务一次网络抖动就得从头再来——而 agent 的任务动辄几十秒，抖动概率比聊天高得多。
    • 





  

  
delta 拼出来的文本，不一定是最终文本。模型可能被截断、被过滤，工具输出也可能乱序。llm_end / tool_end 里要带完整结果，前端以它为准。只信 delta 的实现，会在长回答上偶发地少字、重复字——而且极难复现。





这一章最容易被做错的地方



不是"要不要流式"，是"流的粒度"。按 token 流太碎（一屏几十次重排），按整块流又回到转圈。正确做法是按事件流，在事件内部按 delta 流：界面结构的变更走事件（粗粒度、可预测），文本内容的增长走 delta（细粒度、可合并）。



然后是取消。用户点"停止"时，你要能真的停下来——不只是关掉前端的订阅，还要让后端的 model_call 和 tool_call 收到中断信号。只关前端不关后端，是最常见的"假停止"：界面停了，token 还在烧。



最后，把这十章的线收起来：LLM 提供了能力，工具提供了触达，循环把两者接成行动，中间件把行动变得可控可查，流式把可控可查变成用户能看见的东西。再往上一层就是产品——而产品要解决的，仍然是这十件事。
