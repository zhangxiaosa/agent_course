02 / TOOLS

工具调用的演进

模型从来不会真正"执行"任何东西。它只会生成一段结构化文本，由宿主程序去执行。工具调用的全部演进，改的都是"这段文本长什么样"——而这件事决定了整个生态能不能长起来。

01 · 2023 function calling 模型输出 name + arguments，宿主自己实现路由和校验。手装上了，但每接一个工具都要写一遍胶水。
02 · 2024-11 MCP（Model Context Protocol） Anthropic 发布的开放协议。它标准化的不是模型输出，而是宿主和工具服务器之间的接口。工具终于可以跨应用复用。
03 · 2024 起 code-as-action 模型不再拼参数，直接写一段可执行代码。动作空间从"调用哪个函数"变成"程序能表达的一切"。还不是共识标准，但方向已经清楚。

同一个需求的三个阶段

需求很简单：数出 app.py 里 start_app 出现了多少次。下面按三个阶段切换，看模型实际吐出来的东西差多少。前两个阶段都是调一次 grep，把匹配行回灌给模型，由模型自己数；第三个阶段直接在沙箱里把过滤和计数接成管道，只回传一个数字。

MCP 到底统一了什么



这是最容易被误解的一点：MCP 没有改变模型的输出格式。模型那边仍然是 tool_use 块——和 function calling 时代长得一样。MCP 标准化的是另一条边：工具定义怎么被发现、怎么被调用、结果怎么回来。




  

    
没有标准：每个宿主自己适配每件工具

    

      
    

  


  

    
有 MCP：中间隔一层协议

    

      
    

  





左边是 3 个宿主 × 4 件工具 = 12 套适配，工具换一版就得重写一遍；右边每个宿主只接协议，每件工具只暴露一个 server，总量降到 3 + 4 = 7。中间那一层不生产能力，它只是把组合爆炸换成了加法。



它用 JSON-RPC 2.0 定义了三个原语：tools（可调用的动作）、resources（可读的数据）、prompts（可复用的模板）。传输层可以是 stdio，也可以是 HTTP。于是"写一次工具，给所有客户端用"第一次成为可能——这才是它被称为里程碑的原因：不是技术难度，是把生态的边际成本打下来了。



第三个阶段为什么是 code-as-action



前两个阶段都在优化「参数怎么传」，但它们共享同一个天花板：一次工具调用只能表达一次动作。上面那个需求里，grep 是第一步，计数是第二步——第二步没有对应的工具，只能交给模型在上下文里自己数。



code-as-action 把这个天花板拆了。CodeAct（2024-02）的核心主张是：把动作空间从"一组函数签名"换成"一段可执行代码"。模型写 grep -n start_app app.py | wc -l，过滤和计数在同一段脚本里完成，管道本身承担了原本需要模型接手的那一步。

注意"中间结果"这一行。function calling 时代，一次 grep 把全部匹配行灌进上下文，计数还得由模型完成；code-as-action 时代，管道在沙箱里跑完，模型只拿到 37。上下文成本最低的做法，是根本不产生那些 token。




  

  
安全边界随协议下沉：function calling 时代，危险动作在宿主侧被路由表挡住；MCP 时代，工具来自第三方服务器，宿主必须决定信任谁；code-as-action 时代，模型直接写 shell，沙箱是唯一防线。协议越自由，人工审批层就越不可省。
