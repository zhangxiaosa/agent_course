工具调用的演进

模型从来不会真正"执行"任何东西。它只会生成一段结构化文本，由宿主程序去执行。工具调用的全部演进，改的都是"这段文本长什么样"——而这件事决定了整个生态能不能长起来。

01 · 2023-06-13 function calling 模型输出 name + arguments，宿主自己实现路由和校验。手装上了，但每接一个工具都要写一遍胶水。
02 · 2024-11-25 MCP（Model Context Protocol） Anthropic 发布的开放协议。它标准化的不是模型输出，而是宿主和工具服务器之间的接口。工具终于可以跨应用复用。
03 · 2024-02 → 2025 code-as-action 模型不再拼参数，直接写一段可执行代码。动作空间从"调用哪个函数"变成"程序能表达的一切"。还不是共识标准，但方向已经清楚。

MCP 到底统一了什么



这是最容易被误解的一点：MCP 没有改变模型的输出格式。模型那边仍然是 tool_use 块——和 function calling 时代长得一样。MCP 标准化的是另一条边：工具定义怎么被发现、怎么被调用、结果怎么回来。



没有 MCP：                         有 MCP：
┌────────┐                        ┌────────┐
│  宿主   │─── 自己写的适配层 ───┐   │  宿主   │── MCP Client ──┐
└────────┘   × N 个工具         │   └────────┘                │
                                ↓                              ↓
                          ┌──────────┐                  ┌─────────────┐
                          │ 各家工具  │                  │ MCP Server  │ × N
                          └──────────┘                  └─────────────┘



它用 JSON-RPC 2.0 定义了三个原语：tools（可调用的动作）、resources（可读的数据）、prompts（可复用的模板）。传输层可以是 stdio，也可以是 HTTP。于是"写一次工具，给所有客户端用"第一次成为可能——这才是它被称为里程碑的原因：不是技术难度，是把生态的边际成本打下来了。



第三站为什么是 code-as-action



前两站都在优化"参数怎么传"，但它们共享同一个天花板：一次工具调用只能表达一次动作。模型想做"读文件、过滤、求和"三件事，就得来回三轮。



code-as-action 把这个天花板拆了。CodeAct（2024-02）的核心主张是：把动作空间从"一组函数签名"换成"一段可执行代码"。模型写 sum(1 for l in open('f') if 'error' in l)，一次就完成了读取、过滤、聚合三件事。

注意最后一行"中间结果"——它直接连到第 06 章。function calling 时代，一次跑 ls -R 就是把几万行文件树灌进上下文；code-as-action 时代，这段输出留在沙箱里，模型只拿到 len(result)。上下文压缩最好的办法，是根本不产生那些 token。




  

  
安全边界随协议下沉：function calling 时代，危险动作在宿主侧被路由表挡住；MCP 时代，工具来自第三方服务器，宿主必须决定信任谁；code-as-action 时代，模型直接写 shell，沙箱是唯一防线。协议越自由，第 08 章那个人工审批层就越不可省。
