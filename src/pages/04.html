04 / LOOP

ReAct 循环

把模型和工具装进一个 while 循环里。每一步都把全部历史原样塞回上下文，模型据此产出下一组工具参数。今天绝大多数 coding agent，骨架就是这个环。

while (!done)
model_call tool_call agent_end
checkpoint
messages 记录
READY 这是一个虚构但完整的任务：让 agent 检查 /repo 的 Python 依赖，找出带高危漏洞的包，给出补丁。它手上只有三个工具。点「下一步」，看它怎么用五轮推理走完。
关于数据：案例是教学构造，token 数是示意值，但每轮上下文的增长关系与真实调用一致；工具返回内容为简化后的真实 CVE 记录。

为什么每一次都要"完全重放"

模型不是有状态的进程。model_call 背后是一次无状态的 HTTP 请求：你把一个 messages 数组发过去，它吐出下一段 token，然后忘掉一切。所谓"agent 记住了刚才做过什么"，在实现层面只有一件事——把历史拼进 prompt。

所以每一轮实际发出去的东西长这样：

[
  { "role": "system",    "content": "你是仓库维护 agent…" },
  { "role": "user",      "content": "检查 /repo 的 Python 依赖…" },
  { "role": "assistant", "content": null, "tool_calls": [
      { "id": "c1", "function": { "name": "list_dir",
        "arguments": "{\"path\":\"/repo\"}" } } ] },
  { "role": "tool",      "tool_call_id": "c1", "content": "requirements.txt\napp.py\nREADME.md" },
  { "role": "assistant", "content": null, "tool_calls": [
      { "id": "c2", "function": { "name": "read_file",
        "arguments": "{\"path\":\"/repo/requirements.txt\"}" } } ] },
  { "role": "tool",      "tool_call_id": "c2", "content": "django==3.2.0\nrequests==2.19.0\n…" }
]

注意三件事，它们决定了后面所有章节：

  • 数组只增不减。第 5 轮打的是 10 条消息，不是"当前需要的那两条"。这是上下文单调膨胀的根源。
  • tool_call_id 必须配对。每一条 tool 消息都要指回某个 assistant.tool_calls 里的 id。配对断了，请求直接 400。
  • 模型只产出参数，从不执行。真正跑 list_dir 的是你写的 executor。这一层分离，才是"可以给模型装手"的前提。

循环的三种退出条件

一个能跑的循环，必须同时具备三个出口。缺任何一个，就是烧钱或者卡死：

出口判定方式没有它会怎样
模型自觉完成finish_reason = "stop"，且这次响应里没有 tool_calls——
回合上限turn >= max_turns（常见 20–50）模型反复调用同一个工具，永不收敛
预算上限累计 token 或墙钟时间超阈值一次跑飞的任务吃掉整月额度

第 1 个出口最不可靠：模型完全可以在没查完的情况下给出一个像样的结论。这就是第 09 章 evaluator 中间件要解决的问题——不信任模型的自述，另派一个 judge 对着原始目标验收。

这个循环有三个病灶

环一旦能转起来，问题就从"能不能跑"变成"跑得贵不贵、稳不稳、对不对"。三个病灶分别对应后面的三组中间件：

① 上下文只增不减 —— 历史全集重放，第 30 轮时 prompt 里躺着一堆早已无用的目录列表。→ 上下文压缩、工具输出卸载。

② 参数直接进执行器 —— 模型生成 rm -rf，框架照单执行。→ before_tool 挂起，等人点头。

③ 结束是模型自己说的 —— finish_reason=stop 只代表"它不说话了"，不代表"活干完了"。→ after_agent 加一道验收，不过就跳回去继续。

这三个问题都不是靠改 prompt 能解决的，只能靠在循环的节点上插入可复用的拦截层。那就是第 05 章的主题。
